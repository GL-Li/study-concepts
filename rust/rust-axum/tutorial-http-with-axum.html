HTTP — Build a Web App

Build a tiny task API with Axum and Rust, and learn how each HTTP request and response is actually put together.

How to Use

Create a new Rust project and add the dependencies. Cargo downloads and compiles them on the first build. 

cargo new http-demo
cd http-demo
cargo add axum@0.8.9
cargo add tokio@1.54.1 --features full
cargo add serde@1.0.229 --features derive
cargo add serde_json@1.0.154

Replace the generated src/main.rs with the example below, then start the server: 

cargo run

The versions are the ones this tutorial was tested with; drop the @... parts to get the newest compatible releases. Open a second terminal for the curl commands.

Leave the first terminal running. Cargo compiles on the first run, and the server listens on http://127.0.0.1:8000. It does not reload on edits, so stop it and run cargo run again after changes.

What to observe

Use curl -i so you see the status line and headers, not just the body. Try these in the second terminal, one at a time: 

curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"learn HTTP"}'

curl -i 'http://127.0.0.1:8000/tasks?done=false&limit=5'
curl -i http://127.0.0.1:8000/tasks/1
curl -i -X PUT http://127.0.0.1:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"title":"learn more HTTP","done":true}'
curl -i http://127.0.0.1:8000/whoami -H 'User-Agent: tutorial'
curl -i -X POST http://127.0.0.1:8000/login
curl -i http://127.0.0.1:8000/me
curl -i -X DELETE http://127.0.0.1:8000/tasks/1

The create call answers 201 Created with a Location: /tasks/1 header. The list call includes Cache-Control. The delete call answers 204 No Content with an empty body. Malformed JSON gets 400 Bad Request; JSON that parses but fails the title rule gets 422 Unprocessable Entity.

What You'll Learn

  • How a method plus a path selects a handler (routing).
  • What GET, POST, PUT, and DELETE promise to clients.
  • How JSON request bodies are parsed and validated.
  • How status codes communicate the outcome.
  • Why request and response headers exist, and how to read or set them.
  • How cookies add state to a stateless protocol.
  • How Cache-Control lets clients skip requests.

The Example

A complete, runnable Axum task API. It stores tasks in memory so there is nothing else to set up. The comments point at the HTTP idea each block demonstrates, and the handlers return Response values so the status, headers, and body stay visible. 

use std::collections::BTreeMap;
use std::sync::{Arc, Mutex};

use axum::extract::{Path, Query, State};
use axum::http::{header, HeaderMap, StatusCode};
use axum::response::{IntoResponse, Response};
use axum::routing::{get, post};
use axum::{Json, Router};
use serde::{Deserialize, Serialize};
use serde_json::json;

// Shared, in-memory state. The Mutex makes it safe to use from many tasks.
type Store = Arc<Mutex<StoreInner>>;

#[derive(Default)]
struct StoreInner {
    tasks: BTreeMap<u64, Task>,
    next_id: u64,
}

// The request body schema. serde parses the JSON into this type and
// axum rejects malformed JSON before the handler runs.
#[derive(Deserialize)]
struct TaskIn {
    title: String,
    #[serde(default)]
    done: bool,
}

#[derive(Clone, Serialize)]
struct Task {
    id: u64,
    title: String,
    done: bool,
}

// Query parameters come from the part of the URL after `?`.
#[derive(Deserialize)]
struct ListQuery {
    done: Option<bool>,
    #[serde(default = "default_limit")]
    limit: usize,
}

fn default_limit() -> usize {
    10
}

// Every error response looks like {"detail": "..."} with a useful status.
fn error(status: StatusCode, message: &str) -> Response {
    (status, Json(json!({ "detail": message }))).into_response()
}

// GET is safe: it reads state and must never change it.
async fn list_tasks(State(store): State<Store>, Query(query): Query<ListQuery>) -> Response {
    let store = store.lock().unwrap();
    let mut result: Vec<Task> = store.tasks.values().cloned().collect();
    if let Some(done) = query.done {
        result.retain(|task| task.done == done);
    }
    result.truncate(query.limit);

    // Tell clients the response may be reused for 60 seconds.
    (
        [(header::CACHE_CONTROL, "public, max-age=60")],
        Json(result),
    )
        .into_response()
}

// POST creates a resource. 201 Created plus a Location header tells the
// client where the new resource lives.
async fn create_task(State(store): State<Store>, Json(input): Json<TaskIn>) -> Response {
    if input.title.trim().is_empty() || input.title.chars().count() > 100 {
        return error(
            StatusCode::UNPROCESSABLE_ENTITY,
            "title must be 1-100 characters",
        );
    }

    let mut store = store.lock().unwrap();
    let id = store.next_id;
    store.next_id += 1;
    let task = Task {
        id,
        title: input.title,
        done: input.done,
    };
    store.tasks.insert(id, task.clone());

    (
        StatusCode::CREATED,
        [(header::LOCATION, format!("/tasks/{id}"))],
        Json(task),
    )
        .into_response()
}

// {task_id} is a path parameter: a required part of the URL path.
async fn get_task(State(store): State<Store>, Path(id): Path<u64>) -> Response {
    let store = store.lock().unwrap();
    match store.tasks.get(&id) {
        Some(task) => Json(task.clone()).into_response(),
        None => error(StatusCode::NOT_FOUND, "Task not found"),
    }
}

// PUT replaces the whole resource at a known URL. Repeating the same PUT
// leaves the server in the same state, which is what "idempotent" means.
async fn replace_task(
    State(store): State<Store>,
    Path(id): Path<u64>,
    Json(input): Json<TaskIn>,
) -> Response {
    if input.title.trim().is_empty() || input.title.chars().count() > 100 {
        return error(
            StatusCode::UNPROCESSABLE_ENTITY,
            "title must be 1-100 characters",
        );
    }

    let mut store = store.lock().unwrap();
    if !store.tasks.contains_key(&id) {
        return error(StatusCode::NOT_FOUND, "Task not found");
    }
    let task = Task {
        id,
        title: input.title,
        done: input.done,
    };
    store.tasks.insert(id, task.clone());
    Json(task).into_response()
}

// DELETE removes the resource. 204 No Content means "success, no body".
async fn delete_task(State(store): State<Store>, Path(id): Path<u64>) -> Response {
    let mut store = store.lock().unwrap();
    if store.tasks.remove(&id).is_some() {
        StatusCode::NO_CONTENT.into_response()
    } else {
        error(StatusCode::NOT_FOUND, "Task not found")
    }
}

// The server sends a cookie with Set-Cookie; the browser stores it and
// sends it back automatically on every later request to this site.
async fn login() -> Response {
    (
        [(
            header::SET_COOKIE,
            "session=alice; HttpOnly; Path=/; SameSite=Lax",
        )],
        Json(json!({ "message": "logged in" })),
    )
        .into_response()
}

// Parse the Cookie request header by hand: name=value pairs separated by `;`.
async fn me(headers: HeaderMap) -> Response {
    let session = headers
        .get(header::COOKIE)
        .and_then(|value| value.to_str().ok())
        .and_then(|cookies| {
            cookies
                .split(';')
                .map(str::trim)
                .find_map(|pair| pair.strip_prefix("session="))
        });

    match session {
        Some(user) => Json(json!({ "user": user })).into_response(),
        None => error(StatusCode::UNAUTHORIZED, "Not logged in"),
    }
}

// Read any request header with HeaderMap and add a response header back.
async fn whoami(headers: HeaderMap) -> Response {
    let user_agent = headers
        .get(header::USER_AGENT)
        .and_then(|value| value.to_str().ok())
        .unwrap_or("");

    (
        [("x-powered-by", "axum")],
        Json(json!({ "user_agent": user_agent })),
    )
        .into_response()
}

#[tokio::main]
async fn main() {
    let store: Store = Arc::new(Mutex::new(StoreInner {
        next_id: 1,
        ..Default::default()
    }));

    let app = Router::new()
        .route("/tasks", get(list_tasks).post(create_task))
        .route(
            "/tasks/{task_id}",
            get(get_task).put(replace_task).delete(delete_task),
        )
        .route("/login", post(login))
        .route("/me", get(me))
        .route("/whoami", get(whoami))
        .with_state(store);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:8000")
        .await
        .unwrap();
    println!("listening on http://{}", listener.local_addr().unwrap());
    axum::serve(listener, app).await.unwrap();
}

1. Routing: method + path

A server decides what to run by looking at two things: the HTTP method and the URL path. Together they identify one operation. 

# src/main.rs:54-69
// GET is safe: it reads state and must never change it.
async fn list_tasks(State(store): State<Store>, Query(query): Query<ListQuery>) -> Response {
    let store = store.lock().unwrap();
    let mut result: Vec<Task> = store.tasks.values().cloned().collect();
    if let Some(done) = query.done {
        result.retain(|task| task.done == done);
    }
    result.truncate(query.limit);

    // Tell clients the response may be reused for 60 seconds.
    (
        [(header::CACHE_CONTROL, "public, max-age=60")],
        Json(result),
    )
        .into_response()
}
  • .route("/tasks", get(list_tasks).post(create_task)) registers both methods. A request to /tasks with GET reaches list_tasks.
  • Path parameters are filled from the URL itself. In Axum 0.8 the pattern is /tasks/{task_id} (older versions used :task_id); that part is required.
  • Query parameters come after ? and are optional: ?done=false&limit=5 becomes done=Some(false) and limit=5.
  • Extractors such as State, Query, Path, and Json run before the handler. The handler returns a Response, and .into_response() turns data plus headers into the wire message.

2. Methods carry meaning

The method is not just a label. It tells clients, caches, and proxies whether a request is safe to repeat or safe to prefetch.

Method Safe? Idempotent? Body? In this example
GET Yes Yes No List or read tasks
POST No No Yes Create a task, answer 201 + Location
PUT No Yes Yes Replace a whole task
DELETE No Yes Optional Remove a task, answer 204
PATCH No Not guaranteed Yes Not used here; partial update

    } else {

    }
}
  • Safe means the request does not change server state. A browser or proxy may issue a safe request on its own.
  • Idempotent means repeating the same request has the same final effect as sending it once. PUT and DELETE are idempotent; POST usually is not. A second DELETE may answer 404, but the server state is unchanged.
  • PUT replaces the entire resource. Sending only {"title": "x"} also resets done to its #[serde(default)] value of false. Use PATCH when you mean a partial update.

3. Request bodies and validation

A request body carries the data the client wants to send, usually as JSON with Content-Type: application/json. Axum's Json extractor parses it into a Rust type with serde before your handler runs; your handler adds the business rules.

    done: bool,
}

    title: String,
    done: bool,
}

    }

  • TaskIn describes the body. serde parses the JSON into it, so a missing title or a wrong type is rejected before the handler executes.
  • Malformed JSON gets 400 Bad Request. JSON that parses but breaks the title rule gets 422 Unprocessable Entity from the explicit check.
  • #[serde(default)] makes done optional; when omitted it becomes false. Without it, the field would be required.
  • Json(input) consumes the request body, so the body extractor must be the last handler argument. Unknown fields are ignored by default; add #[serde(deny_unknown_fields)] to reject them.
  • The response is built explicitly: (StatusCode, headers, Json(...)).into_response() maps directly to the status line, headers, and body.

4. Status codes are the contract

The status code is the one-line answer to "what happened?" Clients branch on it, so choosing the right code matters more than the exact reason phrase.

Code Meaning Where in the example
200 OK, with a body GET, PUT
201 Created a new resource POST, with Location
204 Success, intentionally no body DELETE
401 Not authenticated /me without a cookie
400 Malformed request syntax or JSON Json extractor rejection
404 Resource does not exist Unknown task id
422 Body parses but fails a rule Explicit title-length check 
# src/main.rs:99-106

        Some(task) => Json(task.clone()).into_response(),
        None => error(StatusCode::NOT_FOUND, "Task not found"),
    }
}
  • 1xx is informational, 2xx success, 3xx redirection, 4xx the client's problem, and 5xx the server's problem.
  • The error() helper builds a proper response from a status code and a JSON detail, so every failure has the same shape.
  • A 204 response must not include a body. The delete handler returns StatusCode::NO_CONTENT.into_response() for exactly that reason.
  • Do not use 200 for everything. A client that sees 200 will not know the task was missing. Keep 400 (bad syntax) separate from 422 (bad values).

5. Headers: metadata about the message

Headers are key-value pairs on both the request and the response. They describe the message itself: its type, length, caching rules, authentication, and more. 

# src/main.rs:176-188
// Read any request header with HeaderMap and add a response header back.
async fn whoami(headers: HeaderMap) -> Response {
    let user_agent = headers
        .get(header::USER_AGENT)
        .and_then(|value| value.to_str().ok())
        .unwrap_or("");

    (
        [("x-powered-by", "axum")],
        Json(json!({ "user_agent": user_agent })),
    )
        .into_response()
}
  • HeaderMap gives you every request header. Look one up with a constant such as header::USER_AGENT; names are case-insensitive, but values are not.
  • The extra tuple in into_response() adds response headers. Line 65 sets Cache-Control, line 93 sets Location, and line 184 sets x-powered-by.
  • Content-Type tells the receiver how to parse the body; Json sets it to application/json automatically. Accept would tell the server what the client can handle.
  • Custom headers conventionally start with X-. Never put secrets in headers you log.

6. Cookies and statelessness

HTTP itself is stateless: each request stands alone. Cookies add continuity by letting the server store a small token in the client, which the client sends back on later requests. 

# src/main.rs:145-174
// The server sends a cookie with Set-Cookie; the browser stores it and
// sends it back automatically on every later request to this site.
async fn login() -> Response {
    (
        [(
            header::SET_COOKIE,
            "session=alice; HttpOnly; Path=/; SameSite=Lax",
        )],
        Json(json!({ "message": "logged in" })),
    )
        .into_response()
}

// Parse the Cookie request header by hand: name=value pairs separated by `;`.
async fn me(headers: HeaderMap) -> Response {
    let session = headers
        .get(header::COOKIE)
        .and_then(|value| value.to_str().ok())
        .and_then(|cookies| {
            cookies
                .split(';')
                .map(str::trim)
                .find_map(|pair| pair.strip_prefix("session="))
        });

    match session {
        Some(user) => Json(json!({ "user": user })).into_response(),
        None => error(StatusCode::UNAUTHORIZED, "Not logged in"),
    }
}
  • Set-Cookie is a response header. The client stores the value and adds a Cookie request header later.
  • HttpOnly hides the cookie from JavaScript, reducing damage from XSS. SameSite=Lax limits cross-site sending. Use Secure whenever HTTPS is available.
  • Because the protocol is stateless, the cookie is the link between requests. The server still has to look up the session; the cookie is usually just an identifier, not the data itself.
  • This example parses the header by hand to show the wire format. In a real app, use a cookie crate such as axum-extra's CookieJar for signing and robust parsing.
  • Do not store sensitive data directly in a cookie. Store an opaque session id and keep the real state on the server.

7. Caching headers

A cache can reuse a response without asking the server again. The server opts in with response headers such as Cache-Control. 

# src/main.rs:63-68
    // Tell clients the response may be reused for 60 seconds.
    (
        [(header::CACHE_CONTROL, "public, max-age=60")],
        Json(result),
    )
        .into_response()
  • public allows shared caches (including proxies) to store the response. max-age=60 says it stays fresh for 60 seconds.
  • Caching only works because GET is safe and idempotent. Never cache a mutation, and never mark authenticated or private data public.
  • ETag and If-None-Match enable revalidation: the server can answer 304 Not Modified with no body when nothing changed.

Common Pitfalls

Confusing path parameters with query parameters.

/tasks/{task_id} is part of the path and is required. ?done=true is a query parameter and is optional. Putting an identifier in the query string makes the URL less cacheable and less RESTful.

Changing state on GET.

Browsers, prefetchers, and proxies may issue GET requests without the user asking. Use POST, PUT, PATCH, or DELETE for mutations.

Treating PUT like PATCH.

PUT replaces the whole resource, so omitted fields fall back to their #[serde(default)] values. Here that means an omitted done becomes false. If you want "change only this field", use PATCH.

Returning 200 for a creation.

Use 201 Created and add a Location header. Clients then know where the new resource lives.

Forgetting that 204 means no body.

A 204 No Content response must not carry a body. Return StatusCode::NO_CONTENT.into_response() and let the framework end the response.

Caching private data with public.

Cache-Control: public can let shared proxies store the response. Keep authenticated or per-user responses private or uncached.

Putting session data or secrets in a cookie.

Cookies are stored on the client. Store an opaque session id and use HttpOnly, Secure, and an appropriate SameSite policy.

Assuming header names are case-sensitive.

Header names are case-insensitive (User-Agent equals user-agent); header values are not. Let the framework normalize names for you.

Using the old :id route syntax.

Axum 0.8 uses braces: /tasks/{task_id}. A route such as /tasks/:task_id is treated as a literal path and panics during setup unless you explicitly opt into v0.7 checks.

Putting the Json extractor first.

Json consumes the request body, so it must be the last handler argument. Extractors that only read parts of the request, such as State, Path, and HeaderMap, come before it.

Holding a mutex guard across .await.

A std::sync::MutexGuard is not Send, so do not keep one alive across an await point. Lock, copy what you need, drop the guard, then await. These handlers never await while holding the lock.

Inspecting only the body.

Most of the HTTP story is in the status line and headers. Use curl -i or the browser devtools Network tab so you see the whole message.

Key Takeaways

An HTTP exchange is a method plus a path, optional headers, and an optional body on the way in; a status code, headers, and an optional body on the way out. The method's semantics (safe, idempotent) are what let clients, caches, and proxies behave correctly, and the status code is the contract that tells the client what happened.

A web framework mostly removes boilerplate around those pieces. Axum maps methods and paths to handlers, pulls data out with extractors such as Path, Query, and Json, and turns status/header/body tuples into the wire response. Learn the underlying message shape and every framework becomes much easier to reason about.
