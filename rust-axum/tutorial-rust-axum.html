Rust's Axum Framework

Build a tiny JSON HTTP API — routing, extractors, shared state, and typed errors — in about 120 lines.

How to Use

This tutorial assumes you are already comfortable with Rust syntax, traits and generics, async/.await and Tokio, Cargo, HTTP basics, and Result-based error handling. It focuses on Axum and, since it is new to you, on Serde (Rust's serialization framework) in depth.

Create the project and add dependencies:

cargo new notes-api
cd notes-api
cargo add axum
cargo add tokio --features full
cargo add serde --features derive
cargo add serde_json

Paste the full program below into notes-api/src/main.rs, then run it: 

cargo run

In another terminal, exercise the API. Each command below lists the response you should see: 

# 1. Root (plain-text response)
curl localhost:3000/
# Notes API. Try GET /notes

# 2. List notes (JSON response)
curl localhost:3000/notes
# [{"id":1,"title":"Welcome","body":"Your first note"}]

# 3. Get one note by path parameter
curl localhost:3000/notes/1
# {"id":1,"title":"Welcome","body":"Your first note"}

# 4. Create a note (JSON request -> 201 Created)
curl -i -X POST localhost:3000/notes \
  -H 'content-type: application/json' \
  -d '{"title":"Groceries","body":"Milk"}'
# HTTP/1.1 201 Created
# {"id":2,"title":"Groceries","body":"Milk"}

# 5. Query parameter with a serde default
curl 'localhost:3000/notes?limit=1'
# [{"id":1,"title":"Welcome","body":"Your first note"}]

# 6. Missing note -> our custom 404 JSON error
curl -i localhost:3000/notes/99
# HTTP/1.1 404 Not Found
# {"error":"note not found"}
What to observe: responses/status codes change based on the extractors and the return type of each handler. Break the JSON on purpose (-d '{"title":123}') and Axum itself answers 422 — before your handler ever runs.

The Example

One file, no database, no config. It exposes a small in-memory notes API and touches every concept in this tutorial. 

use std::sync::{Arc, Mutex};

use axum::{
    extract::{Path, Query, State},
    http::StatusCode,
    response::{IntoResponse, Response},
    routing::get,
    Json, Router,
};
use serde::{Deserialize, Serialize};

// ---- Shared state -----------------------------------------------------------

#[derive(Clone)]
struct AppState {
    notes: Arc<Mutex<Vec<Note>>>,
}

// ---- Data models (serde) ----------------------------------------------------

#[derive(Debug, Clone, Serialize, Deserialize)]
struct Note {
    id: u64,
    title: String,
    body: String,
}

#[derive(Debug, Deserialize)]
struct NewNote {
    title: String,
    body: String,
}

#[derive(Debug, Deserialize)]
struct ListQuery {
    #[serde(default = "default_limit")]
    limit: usize,
}

fn default_limit() -> usize {
    100
}

// ---- Custom error type ------------------------------------------------------

enum AppError {
    NotFound,
    BadRequest(String),
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, msg) = match self {
            AppError::NotFound => (StatusCode::NOT_FOUND, "note not found".to_string()),
            AppError::BadRequest(m) => (StatusCode::BAD_REQUEST, m),
        };
        (status, Json(serde_json::json!({ "error": msg }))).into_response()
    }
}

// ---- Handlers ---------------------------------------------------------------

async fn root() -> &'static str {
    "Notes API. Try GET /notes"
}

async fn list_notes(State(state): State<AppState>, Query(q): Query<ListQuery>) -> Json<Vec<Note>> {
    let notes = state.notes.lock().unwrap();
    let mut out = notes.clone();
    out.truncate(q.limit);
    Json(out)
}

async fn get_note(State(state): State<AppState>, Path(id): Path<u64>) -> Result<Json<Note>, AppError> {
    let notes = state.notes.lock().unwrap();
    notes
        .iter()
        .find(|n| n.id == id)
        .cloned()
        .map(Json)
        .ok_or(AppError::NotFound)
}

async fn create_note(
    State(state): State<AppState>,
    Json(payload): Json<NewNote>,
) -> Result<(StatusCode, Json<Note>), AppError> {
    if payload.title.trim().is_empty() {
        return Err(AppError::BadRequest("title must not be empty".into()));
    }
    let mut notes = state.notes.lock().unwrap();
    let id = notes.len() as u64 + 1;
    let note = Note {
        id,
        title: payload.title,
        body: payload.body,
    };
    notes.push(note.clone());
    Ok((StatusCode::CREATED, Json(note)))
}

#[tokio::main]
async fn main() {
    let state = AppState {
        notes: Arc::new(Mutex::new(vec![Note {
            id: 1,
            title: "Welcome".into(),
            body: "Your first note".into(),
        }])),
    };

    let app = Router::new()
        .route("/", get(root))
        .route("/notes", get(list_notes).post(create_note))
        .route("/notes/{id}", get(get_note))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    println!("listening on http://{}", listener.local_addr().unwrap());
    axum::serve(listener, app).await.unwrap();
}

1 · Server entry point

Why it matters: Axum has no runtime of its own — you bring Tokio, and you hand a TCP listener plus a Router to axum::serve.

  • #[tokio::main] turns main into a Tokio runtime entry point (you already know this from async Rust).
  • TcpListener is bound first; this lets you print the real address and enables graceful shutdown patterns later.
  • axum::serve(listener, app) drives the Hyper connection loop until the future completes.

2 · Routing

Why it matters: The Router is the table that decides which handler runs for a given method + path.

src/main.rs:112-116

        .route("/", get(root))
        .route("/notes", get(list_notes).post(create_note))
        .route("/notes/{id}", get(get_note))
        .with_state(state);
  • Router::new() starts an empty table; each .route(...) adds one path.
  • A MethodRouter like get(a).post(b) maps different verbs on the same path to different handlers.
  • Captures use braces in Axum 0.8: "/notes/{id}" (older 0.7 used ":id").
  • .with_state(state) attaches shared state — it must be the last builder call before you serve.

3 · Handlers

Why it matters: A handler is just an async fn whose arguments are extractors and whose return type implements IntoResponse.

src/main.rs:63-72

async fn root() -> &'static str {
    "Notes API. Try GET /notes"
}

async fn list_notes(State(state): State<AppState>, Query(q): Query<ListQuery>) -> Json<Vec<Note>> {
    let notes = state.notes.lock().unwrap();
    let mut out = notes.clone();
    out.truncate(q.limit);
    Json(out)
}
  • root returns &'static str, which already implements IntoResponse — that is why it becomes a 200 text body with no ceremony.
  • Everything before the return type are extractors; they are pulled out of the request automatically.
  • Handlers never return Response directly unless you want full control — return ergonomic types and let Axum do the conversion.
Type check, not magic: Axum verifies at compile time that each argument implements FromRequestParts (or FromRequest) and that the return type implements IntoResponse. A wrong signature is a compile error, never a runtime surprise.

4 · Extractors

Why it matters: Extractors are how handlers read the request — path, query, body, headers, or shared state — all in the function signature.

src/main.rs:84-87

async fn create_note(
    State(state): State<AppState>,
    Json(payload): Json<NewNote>,
) -> Result<(StatusCode, Json<Note>), AppError> {
Ordering rule: extractors run left to right. A request body can only be consumed once, so the body-consuming extractor (Json, String, Bytes, …) must be the last argument. Put Json(payload) before State(state) and it won't compile.
  • Parts-based extractors (Path, Query, State, HeaderMap) read the head of the request.
  • Body-based extractors consume the body and therefore come last.
  • You can also wrap an extractor in Result (e.g. Result<Json<T>, JsonRejection>) to handle rejection yourself instead of letting Axum return the error.

5 · Path parameters

Why it matters: Path<T> turns the {...} segments you declared in the route into a typed Rust value.

src/main.rs:74-82

  • The "/notes/{id}" route captures the segment; Path(id): Path<u64> deserializes it into a u64.
  • Multiple captures use a tuple or a struct: Path((a, b)): Path<(u32, u32)> or Path(params): Path<MyParams>.
  • If the segment can't be parsed as the target type, the request is rejected with 400 before your code runs.

6 · Query parameters

Why it matters: Query<T> deserializes the URL query string into a struct — the same Serde machinery as JSON, applied to ?key=value&....

src/main.rs:34-42

#[derive(Debug, Deserialize)]
struct ListQuery {
    #[serde(default = "default_limit")]
    limit: usize,
}

fn default_limit() -> usize {
    100
}
  • Handlers take it as Query(q): Query<ListQuery> (see list_notes at line 67).
  • #[serde(default = "default_limit")] supplies 100 when ?limit= is absent — so GET /notes and GET /notes?limit=1 both work.
  • Because it reuses Serde, any field type that deserializes from a string works: usize, bool, enums, Option<T>, etc.

7 · Serde & JSON

Why it matters: This is the concept that is new to you. Serde ("serialize/deserialize") is the shared translation layer between Rust types and data formats — JSON in our case. Axum's Json extractor and Json response type are both thin wrappers around it.

The two derives

A #[derive(...)] generates the conversion code for you:

DeriveDirectionUse it for
DeserializeJSON text → Rust valuerequest bodies (Json<T> extractor), Query<T>, Path<T>
SerializeRust value → JSON textresponses (Json<T> return type)

src/main.rs:21-32

#[derive(Debug, Clone, Serialize, Deserialize)]
struct Note {
    id: u64,
    title: String,
    body: String,
}

#[derive(Debug, Deserialize)]
struct NewNote {
    title: String,
    body: String,
}
  • Note derives both: it is deserialized in and serialized out.
  • NewNote derives only Deserialize — it is a request payload; the server assigns the id.
  • Modelling input and output separately prevents clients from choosing their own id — a small but important safety habit.

How Rust maps to JSON

Rust typeJSONExample
struct { .. }object{"id":1,"title":"Hi"}
String / &strstring"Hi"
u64, i32, f64number1, 2.5
booltrue / falsetrue
Vec<T>array[{..},{..}]
Option<T> (missing / null)absent or nullnull
HashMap<K,V>object{"a":1}
unit enum variantstring"NotFound"

Field names become JSON keys verbatim, so id serializes as "id". Use attributes to change that:

  • #[serde(rename = "userName")] — different key name.
  • #[serde(rename_all = "camelCase")] — applies the convention to every field.
  • #[serde(skip_serializing_if = "Option::is_none")] — omit a field instead of emitting null.
  • #[serde(default)] / #[serde(default = "fn")] — used in ListQuery above for missing fields.
  • #[serde(deny_unknown_fields)] — reject unexpected keys.

Using it through Axum

The extractor and response wrappers do the wiring:

  • Json(payload): Json<NewNote> deserializes the body (requires header Content-Type: application/json).
  • Returning Json(note) serializes the value and sets the same content type.
Rejections happen before your handler. A missing JSON content type yields 415; malformed or type-mismatched JSON yields 422. Your handler only sees a successfully parsed NewNote — which is why returning 400 for an empty title is something you must do explicitly.

8 · Responses & status codes

Why it matters: Anything implementing IntoResponse can be returned from a handler; tuples let you attach a status code to a body.

src/main.rs:93-100

    let note = Note {
        id,
        title: payload.title,
        body: payload.body,
    };
    notes.push(note.clone());
    Ok((StatusCode::CREATED, Json(note)))
}
  • (StatusCode, Json<T>) is a tuple response: the first element sets the status, the last element is the body.
  • Json<T> requires T: Serialize; it serializes to the body and sets application/json.
  • Returning Json(out) with no tuple defaults to 200 OK, as in list_notes.
  • Other tuple forms exist, e.g. adding headers: (StatusCode, [(header, value)], Json(body)).

10 · Errors

Why it matters: Returning Result<T, E> from a handler is idiomatic — as long as E implements IntoResponse, Axum can turn it into an HTTP response.

  • The handler's return type is Result<OkType, AppError>; ? and return Err(..) both work.
  • Implementing IntoResponse for AppError decides the status code and body in one place.
  • serde_json::json! builds an ad-hoc JSON value, giving a consistent {"error": "..."} shape for clients.
  • In production, log the details and return a generic message so you don't leak internals; keep the rich detail server-side.

Common pitfalls

  • Body extractor not last. Putting Json(..) before another extractor fails to compile because the body can only be consumed once.
  • Wrong capture syntax. Axum 0.8 uses "/notes/{id}". The old ":id" style from 0.7 is no longer valid.
  • Forgetting Content-Type. POSTing JSON without -H 'content-type: application/json' makes Json reject with 415, not 422.
  • Expecting 400 for bad types. Deserialization failures are 422 Unprocessable Entity; do validation inside the handler (as create_note does) for 400.
  • Holding a std::sync::Mutex across .await. This can deadlock or refuse to compile; use tokio::sync::Mutex when the guard must live across await points.
  • Cloning heavy state. Derive Clone but keep the shared data behind Arc; cloning the Vec on every request would defeat the design.
  • Forgetting .with_state(state). Whether you call it or not changes the Router's type, so a missing call is a compile error at serve.
  • Serializing sensitive fields. Don't derive Serialize on a type that holds passwords/secrets, or mark those fields with #[serde(skip)].

Key Takeaways

Axum's design is "types all the way down": routes pick a handler, handlers declare their inputs as extractors and their output as an IntoResponse type, and the compiler checks the wiring. Responses and errors are ordinary Rust values — Json<T>, status tuples, and Result — so once you know Serde and a handful of extractors, the rest is standard Rust.

Start with a Router, one AsyncRead-free handler per route, and share data through State<Arc<Mutex<T>>>; add layers (tracing, timeouts, CORS) later from the Tower ecosystem without rewriting your handlers.
