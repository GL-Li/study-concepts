WebSockets in Web Apps — with Axum

Upgrade an HTTP connection once, then push JSON messages both ways for as long as the connection lives.

How to Use

Create a binary crate and add the crates the example needs. These are current stable versions; axum's ws support is an opt-in feature, so it must be listed explicitly. 

cargo new ws-chat --bin
cd ws-chat
cargo add axum@0.8 --features ws
cargo add tokio@1 --features macros,rt-multi-thread,net,sync
cargo add futures-util@0.3
cargo add serde@1 --features derive
cargo add serde_json@1

Replace the contents of src/main.rs with the code in The Example, then start the server: 

cargo run

Open http://127.0.0.1:3000 in two browser tabs (or two windows). Both pages should show connected. Type a message in one tab and submit it: the message appears in both tabs.

What to observe:

  • In DevTools → Network → WS, select the /ws connection. The status is 101 Switching Protocols.
  • The Messages tab shows green (sent) and white (received) frames such as {"user":"alice","text":"hello"}.
  • Closing one tab leaves the other working. Stopping the server changes both pages to closed (code 1006).

The browser client is embedded in the Rust source as INDEX_HTML, so the whole project is one file. In a real app you would usually serve it with tower-http's ServeDir instead.

The Example

A minimal chat server: every connected browser receives every valid JSON message. The same file serves the page, upgrades /ws, reads and writes concurrently, and broadcasts. 

use axum::{
    extract::{
        ws::{Message, WebSocket, WebSocketUpgrade},
        State,
    },
    response::{Html, Response},
    routing::{any, get},
    Router,
};
use futures_util::{SinkExt, StreamExt};
use serde::{Deserialize, Serialize};
use tokio::sync::broadcast;

const INDEX_HTML: &str = r##"<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <title>axum WebSocket chat</title>
  <style>
    body { font-family: system-ui, sans-serif; max-width: 40rem; margin: 3rem auto; padding: 0 1rem; }
    #log { list-style: none; padding: 0; min-height: 6rem; border: 1px solid #ccc; border-radius: 6px; }
    #log li { padding: 0.4rem 0.7rem; border-bottom: 1px solid #eee; }
    form { display: flex; gap: 0.5rem; margin-top: 1rem; }
    input { padding: 0.4rem; }
    #status { color: #666; font-size: 0.9rem; }
  </style>
</head>
<body>
  <h1>axum WebSocket chat</h1>
  <p id="status">connecting...</p>
  <ul id="log"></ul>
  <form id="form">
    <input id="user" value="alice" size="8" />
    <input id="text" placeholder="say something" size="30" autocomplete="off" />
    <button>Send</button>
  </form>
  <script>
    const logEl = document.getElementById("log");
    const statusEl = document.getElementById("status");
    const ws = new WebSocket(`ws://${location.host}/ws`);

    ws.onopen = () => { statusEl.textContent = "connected"; };
    ws.onclose = (event) => {
      statusEl.textContent = `closed (code ${event.code})`;
    };
    ws.onmessage = (event) => {
      const message = JSON.parse(event.data);
      const li = document.createElement("li");
      li.textContent = `${message.user}: ${message.text}`;
      logEl.append(li);
    };

    document.getElementById("form").addEventListener("submit", (event) => {
      event.preventDefault();
      if (ws.readyState !== WebSocket.OPEN) return;
      const user = document.getElementById("user").value;
      const text = document.getElementById("text").value;
      ws.send(JSON.stringify({ user, text }));
      document.getElementById("text").value = "";
    });
  </script>
</body>
</html>
"##;

#[derive(Debug, Serialize, Deserialize)]
struct ChatMessage {
    user: String,
    text: String,
}

#[derive(Clone)]
struct AppState {
    tx: broadcast::Sender<String>,
}

async fn index() -> Html<&'static str> {
    Html(INDEX_HTML)
}

async fn ws_handler(State(state): State<AppState>, ws: WebSocketUpgrade) -> Response {
    ws.on_upgrade(|socket| handle_socket(socket, state))
}

async fn handle_socket(socket: WebSocket, state: AppState) {
    let (mut sender, mut receiver) = socket.split();
    let mut rx = state.tx.subscribe();
    let tx = state.tx.clone();

    let mut send_task = tokio::spawn(async move {
        loop {
            match rx.recv().await {
                Ok(text) => {
                    if sender.send(Message::text(text)).await.is_err() {
                        break;
                    }
                }
                Err(broadcast::error::RecvError::Lagged(n)) => {
                    eprintln!("client lagged behind by {n} messages");
                }
                Err(broadcast::error::RecvError::Closed) => break,
            }
        }
    });

    let mut recv_task = tokio::spawn(async move {
        while let Some(Ok(message)) = receiver.next().await {
            match message {
                Message::Text(text) => {
                    if let Ok(chat) = serde_json::from_str::<ChatMessage>(text.as_str()) {
                        if let Ok(json) = serde_json::to_string(&chat) {
                            let _ = tx.send(json);
                        }
                    }
                }
                Message::Close(_) => break,
                _ => {}
            }
        }
    });

    tokio::select! {
        _ = &mut send_task => recv_task.abort(),
        _ = &mut recv_task => send_task.abort(),
    }
}

#[tokio::main]
async fn main() {
    let (tx, _) = broadcast::channel(32);
    let state = AppState { tx };

    let app = Router::new()
        .route("/", get(index))
        .route("/ws", any(ws_handler))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("open http://127.0.0.1:3000");
    axum::serve(listener, app).await.unwrap();
}

1. What a WebSocket is

Why it matters: a WebSocket is not a different transport. It is an ordinary HTTP request that asks the server to stop speaking HTTP and keep the TCP connection open for messages in both directions.

HTTP request/response WebSocket
Who sends Client initiates, server replies Either side, at any time
Lifetime One exchange; connections may be reused One connection until either side closes
Unit Request and response bodies Text or binary messages
Server push Polling, long-polling, or SSE workarounds Native; the server writes whenever it wants
Metadata Headers repeated on every request One handshake; no per-message headers

What HTTP cannot do (practically)

Strictly speaking, HTTP can emulate most real-time behaviour with polling, long-polling, or Server-Sent Events plus POST requests. What it cannot do efficiently is keep one connection open for true bidirectional, low-latency exchange — either side sending at any time, with no request/response pairing and no repeated headers.

  • Chat and presence: every participant must receive messages immediately while also sending their own.
  • Multiplayer games and collaborative editing: many small updates flow in both directions with minimal latency.
  • Live dashboards, trading feeds, and notifications: server state changes must reach the client as it happens, not on the next poll.

What the browser API gives you

  • The browser API is message-oriented, not a raw TCP socket. The protocol supplies framing, UTF-8 checks, client-to-server masking, ping/pong, and a close handshake.
  • It uses the same host and port as the page: ws:// follows http:// and wss:// follows https://.
  • In axum, the endpoint is just another route. The only unusual part is the extractor that performs the upgrade.

main.rs:133-136

let app = Router::new()
    .route("/", get(index))
    .route("/ws", any(ws_handler))
    .with_state(state);

any rather than get matters: HTTP/1.1 upgrades use GET, while HTTP/2 uses CONNECT (RFC 8441). any accepts both, so the endpoint keeps working if the server is later served over HTTP/2.

2. The HTTP upgrade

Why it matters: everything before the 101 response is ordinary HTTP, which is why cookies, middleware, and origin checks still apply.

The client's HTTP/1.1 request looks like this:

GET /ws HTTP/1.1
Host: 127.0.0.1:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
  • Sec-WebSocket-Key is a random nonce. The server replies with Base64(SHA-1(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11")), proving it understood the upgrade.
  • axum's WebSocketUpgrade extractor validates the request headers and prepares the 101 response. It is a FromRequestParts extractor, so it composes with State and other parts extractors.
  • on_upgrade returns the HTTP response immediately and runs your callback in a background task. The callback's future has already left HTTP behind, so its errors cannot become status codes.

main.rs:81-83

    ws.on_upgrade(|socket| handle_socket(socket, state))
}

3. Messages and frames

Why it matters: the WebSocket protocol sends frames; your code works with whole messages. Knowing the five message kinds explains most of the lifecycle behaviour you will observe.

Message Meaning Who handles it
Text UTF-8 application data; JSON here Your code
Binary Arbitrary bytes (files, protobuf, images) Your code
Ping Liveness check; payload at most 125 bytes Answered automatically with Pong
Pong Reply to a Ping, or an unsolicited heartbeat Sent automatically after a Ping
Close Graceful shutdown, with an optional code and reason Replied to automatically; then the stream ends
  • A message can be split across several frames. axum reassembles them and gives you a Message; max_message_size limits the reassembled result.
  • Clients must mask their frames; servers must not. The underlying tungstenite implementation enforces this, and rejects unmasked client frames by default.
  • In axum 0.8, Message::Text holds a Utf8Bytes, not a String. Use text.as_str() to borrow it and Message::text(...) to build one.

4. A JSON protocol with serde

Why it matters: WebSocket gives you messages, not structure. A versioned, validated format is what keeps the two ends compatible.

main.rs:66-70

#[derive(Debug, Serialize, Deserialize)]
struct ChatMessage {
    user: String,
    text: String,
}
  • The browser sends JSON.stringify({user, text}); the server parses into ChatMessage and re-serializes. Re-serializing validates the shape before any browser sees it.
  • Malformed input is ignored by the if let Ok. One bad client must not make every other client's JSON.parse throw.
  • user is client-supplied here. A real app should take the identity from the authenticated session, not the payload.

main.rs:109-115

Message::Text(text) => {
    if let Ok(chat) = serde_json::from_str::<ChatMessage>(text.as_str()) {
        if let Ok(json) = serde_json::to_string(&chat) {
            let _ = tx.send(json);
        }
    }
}

On the wire the frame carries a string. If you later need binary payloads, send Message::Binary with a format such as MessagePack or protobuf, and keep a type tag in the payload so the protocol can evolve.

5. Full-duplex needs two tasks

Why it matters: a chat server must wait for this client's next message and deliver messages from other clients at the same time. A single recv/send loop cannot do both.

For an echo endpoint this loop is enough: while let Some(msg) = socket.recv().await { socket.send(msg).await? }. But while that loop is blocked in recv, nothing else can write to the socket, and a single WebSocket value cannot be borrowed mutably by two tasks.

StreamExt::split turns one socket into a SplitSink (write half) and a SplitStream (read half). Each half is moved into its own task. The tasks are independent and can make progress concurrently.

main.rs:85-120

let (mut sender, mut receiver) = socket.split();
let mut rx = state.tx.subscribe();
let tx = state.tx.clone();

let mut send_task = tokio::spawn(async move {
    ...
});

let mut recv_task = tokio::spawn(async move {
    while let Some(Ok(message)) = receiver.next().await {
        ...
    }
});

select! then ties the two tasks together; the next section shows the exact code. This pattern — split, spawn, select — is the standard shape for any non-trivial WebSocket handler.

6. Broadcast fan-out

Why it matters: every connection owns its write half, but a message arriving on one connection must reach all the others. tokio's broadcast channel is a one-to-many queue designed exactly for that.

main.rs:72-75

#[derive(Clone)]
struct AppState {
    tx: broadcast::Sender<String>,
}

main.rs:130-131

let (tx, _) = broadcast::channel(32);
let state = AppState { tx };
  • 32 is the capacity of a ring buffer, not a maximum number of clients. If a receiver falls more than 32 messages behind, older ones are dropped and recv() returns RecvError::Lagged(n).
  • The example logs the lag and keeps going. For a stricter chat you might disconnect the slow client instead (break), or keep a per-client backlog.
  • mpsc is the wrong tool: its receiver is a single consumer. watch is also wrong: it keeps only the latest value, discarding intermediate messages.
  • Each message is a cloned String, so N clients means N allocations per message. For high fan-out, send an Arc<str> or Bytes instead.

...

7. The browser client

Why it matters: the browser side is where the connection actually starts, and where lifecycle bugs (sending before open, no reconnect) usually live.

main.rs:38-60 (the embedded INDEX_HTML string)

const logEl = document.getElementById("log");
const statusEl = document.getElementById("status");
const ws = new WebSocket(`ws://${location.host}/ws`);

ws.onopen = () => { statusEl.textContent = "connected"; };
ws.onclose = (event) => {
  statusEl.textContent = `closed (code ${event.code})`;
};
ws.onmessage = (event) => {
  const message = JSON.parse(event.data);
  const li = document.createElement("li");
  li.textContent = `${message.user}: ${message.text}`;
  logEl.append(li);
};

document.getElementById("form").addEventListener("submit", (event) => {
  event.preventDefault();
  if (ws.readyState !== WebSocket.OPEN) return;
  const user = document.getElementById("user").value;
  const text = document.getElementById("text").value;
  ws.send(JSON.stringify({ user, text }));
  document.getElementById("text").value = "";
});
  • new WebSocket(url) sends the upgrade request and puts the object in CONNECTING (0). It becomes OPEN (1) when the 101 arrives; calling send before that throws.
  • onmessage fires once per message. For text frames, event.data is a string; for binary frames it is a Blob or ArrayBuffer depending on binaryType.
  • Use wss:// when the page is served over HTTPS. Browsers block ws:// as mixed content. Deriving the URL from location avoids hardcoding the host.
  • There is no automatic reconnection. Real clients loop with exponential backoff and re-establish subscriptions after onclose.
  • textContent, not innerHTML: chat text is untrusted and must not be parsed as HTML.

8. Lifecycle and cleanup

Why it matters: sockets die in several ways, and a leaked task or receiver keeps resources alive long after the browser is gone.

main.rs:122-125

tokio::select! {
    _ = &mut send_task => recv_task.abort(),
    _ = &mut recv_task => send_task.abort(),
}
  • Graceful close: the client sends a Close frame. The read loop matches Message::Close(_), breaks, and select! aborts the write task. axum has already queued the automatic Close reply.
  • Abrupt disconnect: the browser tab is killed or the network drops. recv ends or errors, and send returns an error. Either task finishing triggers the same cleanup.
  • When both halves are dropped, the broadcast receiver is dropped too, so the connection stops counting as a subscriber. There is no separate registry to clean up in this example.
  • If you do keep a user list in shared state, remove the entry on every exit path — a guard type with a Drop impl is more reliable than duplicating cleanup in each break.
  • To close deliberately, send Message::Close(Some(CloseFrame { code: 1000, reason: "bye".into() })) before dropping. Dropping without a close frame is allowed but gives the peer an abnormal-closure code such as 1006.

9. Limits, origin, and auth

Why it matters: a WebSocket bypasses two protections people assume they have — per-request authorization checks and CORS.

Start with limits. The defaults are generous (64 MiB per message, 16 MiB per frame); a chat does not need that:

variation of ws_handler, main.rs:81-83

async fn ws_handler(State(state): State<AppState>, ws: WebSocketUpgrade) -> Response {
    ws.max_message_size(64 * 1024)
        .on_upgrade(|socket| handle_socket(socket, state))
}
  • Origin: browsers do not apply CORS to WebSockets. Any page can open a socket to your server, and the browser will attach your cookies (subject to SameSite). Check the Origin header during the handshake (a middleware or a guard extractor) and reject unexpected origins. Non-browser clients can forge it, so this is not authentication.
  • Auth: the handshake is a normal HTTP request, so existing cookie middleware runs before the upgrade. The browser WebSocket API cannot set an Authorization header; HttpOnly session cookies are the usual approach. Avoid tokens in the query string because URLs end up in logs and history.
  • Timeouts: proxies and load balancers often kill idle connections. Send periodic Ping frames or app-level heartbeats, and have clients reconnect. Browsers answer pings automatically.
  • Multiple instances: this broadcast channel lives in one process. With several axum instances behind a load balancer, a message reaches only clients connected to the same process. Use an external pub/sub (Redis, NATS, Postgres LISTEN/NOTIFY) to bridge instances.
  • Backpressure: the bounded broadcast channel protects memory by dropping old messages for slow consumers. Decide deliberately whether to skip, buffer, or disconnect when Lagged appears.

Common Pitfalls

Forgetting the ws feature

Without --features ws, axum::extract::ws does not exist. The import error looks unrelated at first.

Routing /ws with get only

HTTP/1.1 upgrades use GET, but HTTP/2 uses CONNECT. any(ws_handler) covers both.

Using one task for both directions

An echo loop works because every read has a write. Chat does not. Split the socket, or the connection cannot receive server pushes while it waits for the client.

Trying to clone an mpsc::Receiver

A single-consumer channel cannot fan out. Use broadcast and call subscribe() once per connection.

Swallowing RecvError::Lagged

while let Ok(msg) = rx.recv().await exits silently when a slow client lags, so that client stops receiving forever. Handle Lagged explicitly.

Trusting the client's user field

The demo lets the client choose its name. In production, derive the sender from the authenticated session so clients cannot impersonate each other.

Sending before the socket is open

In the browser, send on a socket in CONNECTING throws. Queue input until onopen fires, or check readyState === WebSocket.OPEN.

Assuming onclose always fires

Abrupt network loss may not produce a close event promptly. Pair the client with a heartbeat and a reconnect loop rather than waiting forever.

Using ws:// from an HTTPS page

Browsers block it as mixed content. Use wss:// and have the server terminate TLS (directly or at a proxy).

Treating WebSocket as request/response RPC

Messages have no IDs or replies built in. If you need request/response, add a correlation ID and a pending-request map to your protocol.

Key Takeaways

A WebSocket is one HTTP connection upgraded out of HTTP, then used for framed messages in both directions. In axum, the WebSocketUpgrade extractor produces the 101 response and hands the socket to a plain async task. For anything beyond echo, split the socket, run a read task and a write task, tie them together with select!, and fan messages out through a tokio broadcast channel. Remember that the handshake is still HTTP — which is exactly where origin checks and authentication belong — and that the process-local broadcast does not cross server instances.
