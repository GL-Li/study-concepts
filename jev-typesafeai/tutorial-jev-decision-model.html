Jev: The Decision Model

Jev is a System One model: you send it state plus typed questions, and it returns numbers — never prose. Your code turns those numbers into the decision.

How to Use

Create a project, add the SDK, and run the single-file example:

uv init
uv add typesafe-sdk httpx2
uv run main.py

The example runs offline by default: if TYPESAFE_API_KEY is not set, the client replays a recorded jev-1.13.0 answer so you can read every part of the flow immediately. Export a real key to hit the live model instead:

export TYPESAFE_API_KEY=your-key
uv run main.py

Expected output (the values are probabilities, so a live run will differ slightly):

model                        : jev-1.13.0
duplicate_charge  (noul)     : 0.97
request_type      (choice)   : refund (confidence 0.91)
frustration       (score)    : 1.60
decision                     : auto_refund

What You'll Learn

  • What a System One decision model is, and how it differs from an LLM.
  • How state carries the content Jev evaluates, separate from the questions.
  • How to ask many atomic questions in one parallel request.
  • The three primitives — Noul Choice Score — and the answer shape of each.
  • How to read probabilities and confidence as actionable numbers.
  • How code turns typed answers into a routing decision with thresholds.
  • Why low-confidence answers should escalate to a human.
  • Why broad questions must be decomposed into atomic ones.

The Example

This is the complete program. Copy it into main.py after running the setup commands above. (To run it offline before adding a key, keep it exactly as written — make_client chooses the replay transport for you.)

"""A minimal Jev decision-model example.

One request, three typed questions, and a decision made in ordinary code.
Runs offline (replaying a recorded answer) unless TYPESAFE_API_KEY is set.
"""

import os

import httpx2
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

# 1. STATE  --  the content Jev evaluates. One structured object, not a prompt.
STATE = {
    "ticket": {
        "subject": "Duplicate charge on order A-104",
        "message": (
            "I was charged twice for order A-104. This is the third time "
            "I've written in. Please refund the duplicate."
        ),
    },
    "order": {
        "id": "A-104",
        "charges": [
            {"amount_usd": 49, "status": "captured"},
            {"amount_usd": 49, "status": "captured"},
        ],
    },
    "refund_policy": "Duplicate charges are eligible for a full refund.",
}

# 2. QUESTIONS  --  three primitives asked together in one request.
#    The ids are for our code; only instructions/criteria reach the model.
QUESTIONS = {
    "duplicate_charge": Noul(
        instructions="Do `order.charges` show the same amount captured more than once?",
    ),
    "request_type": Choice(
        instructions="What is the main request in `ticket.message`?",
        criteria={
            "refund": "The customer wants money returned.",
            "rebooking": "The customer wants the item reshipped.",
            "information": "The customer is asking for information only.",
        },
    ),
    "frustration": Score(
        instructions="How frustrated does the customer appear in `ticket.message`?",
        criteria=[
            "Calm and neutral.",
            "Concerned but civil.",
            "Very angry or using strong language.",
        ],
    ),
}

# A recorded jev-1.13.0 answer for the state above, used when no API key is set.
RECORDED = {
    "model": "jev-1.13.0",
    "answers": {
        "duplicate_charge": {"type": "noul", "noul": 0.97},
        "request_type": {
            "type": "choice",
            "choice": "refund",
            "confidence": 0.91,
            "probabilities": {"refund": 0.94, "rebooking": 0.02, "information": 0.04},
        },
        "frustration": {
            "type": "score",
            "score": 1.60,
            "confidence": 0.40,
            "legend": {
                0: "Calm and neutral.",
                1: "Concerned but civil.",
                2: "Very angry or using strong language.",
            },
            "probabilities": {0: 0.0, 1: 0.40, 2: 0.60},
        },
    },
    "usage": {"input_tokens": 412, "output_tokens": 41},
}


def make_client() -> TypeSafeClient:
    """Real client when TYPESAFE_API_KEY is set; offline replay otherwise."""
    if os.environ.get("TYPESAFE_API_KEY"):
        return TypeSafeClient(timeout=30.0)
    replay = httpx2.MockTransport(lambda _request: httpx2.Response(200, json=RECORDED))
    return TypeSafeClient(api_key="offline", transport=replay)


# 3. DECIDE  --  code owns the policy. Thresholds are constants, not prompts.
APPROVE_AT = 0.90  # noul: act only on a confident yes
REVIEW_BELOW = 0.70  # confidence: below this, a person reviews


def decide(response) -> str:
    answers = response.answers
    duplicate = answers["duplicate_charge"].noul
    request = answers["request_type"]

    if request.confidence < REVIEW_BELOW:
        return "route_to_human: intent unclear"
    if request.choice == "refund" and duplicate >= APPROVE_AT:
        return "auto_refund"
    if duplicate >= APPROVE_AT:
        return f"route_to_{request.choice}"
    return "route_to_human: policy not satisfied"


def main() -> None:
    with make_client() as client:
        response = client.system_one(state=STATE, questions=QUESTIONS)

    answers = response.answers
    print(f"model                        : {response.model}")
    print(f'duplicate_charge  (noul)     : {answers["duplicate_charge"].noul:.2f}')
    print(
        f'request_type      (choice)   : {answers["request_type"].choice} '
        f'(confidence {answers["request_type"].confidence:.2f})'
    )
    print(f'frustration       (score)    : {answers["frustration"].score:.2f}')
    print(f"decision                     : {decide(response)}")


if __name__ == "__main__":
    main()

A Decision Model, Not an LLM

Why it matters: everything Jev does follows from the fact that its output is a number your program reads, not text a person reads.

An LLM generates the next token. To get a usable field out of it you prompt for JSON and then parse — and hope the shape holds. Jev is a System One model: it was trained to make one fast, calibrated judgment at a time and return it as a constrained value. It does not write answers, produce code, or explain itself.

LLMJev (System One)
OutputFree-form textTyped value + probabilities
You mustParse the responseRead a field
Can it invent values?Yes, outside your schemaNo — confined to your options
UncertaintyUsually hiddenCalibrated probability
Role in the systemGenerates the answerMakes one narrow judgment
The name: "System One" comes from Kahneman's Thinking, Fast and Slow — fast, intuitive judgments. Jev is TypeSafe's flagship System One model.

State: What Gets Evaluated

Why it matters: state is the content; questions are the judgments about it. Keeping them separate is what makes the request reusable.

State is whatever Jev looks at to answer your questions. It can be a string, but a structured object is usually better: each part gets a name, and questions can point at a specific part with a backticked path like `order.charges`.

    },

  • One state, many parts. The ticket, the order, and the refund policy live together because the decision needs to compare them.
  • Facts, not instructions. State contains the material to judge; the questions state what to judge about it.
  • Paths remove ambiguity. `order.charges` tells Jev exactly which field to inspect instead of guessing from the whole blob.
Watch out: Jev currently accepts text only (strings, JSON objects, arrays of text). No images, audio, or video. Its strongest language is English.

One Request, Many Questions

Why it matters: questions run in parallel and independently, so asking three costs barely more than asking one — and no answer contaminates another.

Every question that uses the same state goes into a single call:

main.py:110-111 
    with make_client() as client:
        response = client.system_one(state=STATE, questions=QUESTIONS)
  • Ids are for you. duplicate_charge, request_type, frustration label the answers in your code. They are never sent to the model.
  • Parallel and isolated. Adding a question does not lengthen the response or change the other answers.
  • Ask speculatively. A question whose answer you might ignore for some inputs is nearly free — the code simply does not read it.

The Three Primitives

Why it matters: match the question type to the shape of the answer your code can act on — a category, a spectrum, or a yes/no.

PrimitiveAnswersReturnsUse when
NoulIs this true?noul (0–1)A clean yes/no where the probability is the signal
ChoiceWhich of these?choice, probabilities, confidenceOptions with no order between them
ScoreWhich level?score, legend, probabilities, confidenceA spectrum you can describe in steps

Noul — a probability that the answer is yes

A Noul returns one number. Near 1 is a strong yes, near 0 a strong no, near 0.5 means yes and no are about equally likely. It is not a scale of degree.

Design rule: each question asks one well-scoped thing — "a judgment a knowledgeable person could make in a few seconds." If a question weighs several factors, split it (see Decompose).

Answers Are Typed Numbers

Why it matters: probabilities and confidence are the raw material your policy is written on top of — not decoration.

The response is a dict of answer objects, each typed to its question. Read the fields directly:

main.py:113-120 
    answers = response.answers
    print(f"model                        : {response.model}")
    print(f'duplicate_charge  (noul)     : {answers["duplicate_charge"].noul:.2f}')
    print(
        f'request_type      (choice)   : {answers["request_type"].choice} '
        f'(confidence {answers["request_type"].confidence:.2f})'
    )
    print(f'frustration       (score)    : {answers["frustration"].score:.2f}')
  • choice / score / noul — the selected value. For Score it is the probability-weighted mean, so it can be fractional.
  • probabilities — the full distribution over your options or levels; it sums to 1.
  • confidence — one number from the shape of that distribution: 1.0 when all probability sits on one outcome, lower the more it spreads. Noul has no separate confidence; its single probability already carries the uncertainty.

How these two confidences are computed

confidence is not a separate model output: it is a statistic of the probabilities the answer already carries. All the probability on one outcome gives 1.0, an even spread gives 0.0. TypeSafe computes it for you, and the two values in the figure come straight from the formulas below.

Choice measures how far the top option sits above an even split of 1/n, where n is the number of options:

request_type — n = 3 options, top probability p_max = 0.94 (refund)confidence = (p_max − 1/n) / (1 − 1/n) = (0.94 − 1/3) / (1 − 1/3) = 0.607 / 0.667 ≈ 0.91

Score also counts how far the probability sits from the most likely level, because its levels are ordered:

frustration — n = 3 levels, most likely level m = 2 (angry)spread = Σ pᵢ·|i − m| = 0.40×|1 − 2| + 0.60×|2 − 2| = 0.40 # MAD_unif — mean absolute deviation of a uniform (evenly spread) distribution MAD_unif = (1/n)·Σ |i − (n−1)/2| = (|0 − 1| + |1 − 1| + |2 − 1|) / 3 = 2/3 ≈ 0.67 confidence = max(0, 1 − spread / MAD_unif) = 1 − 0.40 / 0.67 ≈ 0.40
Noul has no separate confidence. Its one probability already describes both outcomes completely. If you want a value on the same 0–1 scale — for example to gate Nouls and Choices with one piece of code — use |2p − 1|, which is 0 at p = 0.5 and 1 at p = 0 or 1.
Two different distributions can share one number. A score of 1.0 can mean all probability on level 1, or half on level 0 and half on level 2. Read probabilities and confidence alongside the value.

Code Decides

Why it matters: the model supplies judgment; your program supplies policy. Keeping thresholds as ordinary constants makes them reviewable and tunable.

Jev never says "approve" or "route to billing". It answers questions. The decision — an ordered list of if rules — lives in your code:

main.py:90-106 
# 3. DECIDE  --  code owns the policy. Thresholds are constants, not prompts.
APPROVE_AT = 0.90  # noul: act only on a confident yes
REVIEW_BELOW = 0.70  # confidence: below this, a person reviews


def decide(response) -> str:
    answers = response.answers
    duplicate = answers["duplicate_charge"].noul
    request = answers["request_type"]

    if request.confidence < REVIEW_BELOW:
        return "route_to_human: intent unclear"
    if request.choice == "refund" and duplicate >= APPROVE_AT:
        return "auto_refund"
    if duplicate >= APPROVE_AT:
        return f"route_to_{request.choice}"
    return "route_to_human: policy not satisfied"
  • Thresholds are constants. Changing a number is a reviewed code edit, not a reworded prompt.
  • Compose multiple answers. Here the decision needs two questions together: the intent and whether the policy condition holds.
  • Weighted sums work too. For several Score questions, normalize each and combine with weights you control, e.g. 0.6*severity + 0.3*frustration + 0.1*report_quality.

Route on Uncertainty

Why it matters: a decision model you cannot trust on edge cases is not usable. Confidence gives the model a principled way to say "I'm not sure."

The first rule in decide is the most important one: if the intent is unclear, do not guess — send it to a person.

The red and yellow bands both involve a person, but they are different situations. In the red band the model has no usable read, so a person decides the outcome from scratch. In the yellow band the model does have a probable answer; the risk is acting on it unverified, so you confirm it — ask the user, run a cheap check, or flag it for review — and only then act. In the green band you act directly.

  • Three paths. High confidence acts; medium confidence reviews or confirms; low confidence escalates.
  • Different actions, different bars. A read-only screen can act at lower confidence than a destructive operation.
  • Tune with data. Plot confidence against accuracy on your own inputs and move the lines; the values here are a starting point, not gospel.

Decompose the Judgment

Why it matters: a broad question hides several judgments behind one number. Atomic questions expose them so you can inspect, weight, and tune each one.

Ask one narrow thing per question. Instead of "Is this ticket ready to auto-refund?", this example asks the two independent sub-judgments — duplicate_charge (a Noul) and request_type (a Choice) — and combines them in decide. Need frustration too? Add a third question; the request count stays at one.

Broad (avoid)Atomic (do)
"Should we refund this order?"duplicate_charge · request_type · frustration
"Is this message spam?"requests_credentials · sender_identity_mismatch · unexpected_reward
"Rate this candidate"market · feasibility · differentiation, each its own Score
  • Decomposition costs nothing extra in round trips. The pieces run in parallel inside the one request.
  • Weights live in code. When a combined result does not match your team's decision, change a coefficient and re-run — no prompt rewrite.
  • Combine with an if or a weighted sum. Atomic answers make ordinary, testable logic possible.

Common Pitfalls

  • Treating a Noul as a measurement. A value of 0.5 means yes and no are equally likely — not "medium skill" or "medium severity." If you want degree, use a Score with defined levels.
  • Phrasing a Noul so a high value means "no." "Is the message free of personal data?" inverts the meaning and code reads it backwards. Phrase so a high value means yes.
  • Numeric-only Score levels. Levels like ["0", "1", "2"] give the model nothing to match against. Describe situations: "Blocking issue; no workaround exists."
  • One request per question. Questions on the same state are parallel and cheap to add; batching is dramatically faster and cheaper than many round trips.
  • Ignoring confidence. Acting on a flat distribution is how you confidently do the wrong thing. Route the middle and the low to review.
  • Reading only the score. A fractional score hides the distribution behind it; check probabilities and confidence when the call matters.
  • Putting policy in the prompt. "Refund only if clearly a duplicate" belongs in a threshold in code, where it can be reviewed, tested, and changed.

Key Takeaways

Jev is a decision model: you give it state and typed questions, it returns constrained values and calibrated probabilities, and your code does the rest. Ask each judgment as a small atomic question, batch them into one parallel request, then combine the answers with thresholds and confidence gates you own. The model supplies judgment about unstructured content; your program keeps control of the workflow and the policy.
