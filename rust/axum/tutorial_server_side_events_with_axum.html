Server-Sent Events with axum

Build a one-way, always-open event stream from a Rust server to a browser — with fan-out to many clients, keep-alives, and a working EventSource client.

How to Use

Create a new binary crate and add the four dependencies. The versions below are the ones this tutorial was verified against with Rust 1.95.

terminal
cargo new sse-demo
cd sse-demo
cargo add axum@0.8.9
cargo add tokio@1.54.1 --features full
cargo add tokio-stream@0.1.19 --features sync
cargo add futures-util@0.3.34

Replace the contents of src/main.rs with The Example below, then run it.

terminal
cargo run

Open http://127.0.0.1:3000 in two tabs, and in a third terminal watch the raw stream with curl. -N turns off curl's output buffering so events appear as they arrive.

terminal · curl
curl -N http://127.0.0.1:3000/events

You should see frames arrive once per second, like this (your numbers start wherever the server's clock is):

expected output
event: tick
id: 3
data: tick #3

event: tick
id: 4
data: tick #4

event: tick
id: 5
data: tick #5

In the browser, the status flips to connected and a new list item appears each second showing the payload and its id. Both tabs receive the same tick numbers: this is fan-out, not two independent timers.

What to observe: the response stays open instead of completing — this is one HTTP request carrying an open-ended body. Stop the server and the response ends; the browser status becomes reconnecting…, and events resume when it restarts.

What You'll Learn

  • Why an SSE endpoint is one long-lived HTTP response rather than a stream of requests, and how that differs from WebSockets and polling.
  • Why the text/event-stream frame format needs a blank dispatch line, and what data, event, id, and retry each control on the client.
  • Why an open-ended response does not block a thread: the body is an async stream, and Pending parks the task instead of spinning.
  • Why fan-out needs one independent receiver per connection, and why a broadcast channel provides exactly that.
  • Why channel capacity is a data-loss policy, and what a lagging subscriber experiences.
  • Why an open-ended response still needs idle keep-alives, and when those keep-alives appear.
  • Why the event source can be a plain task with no knowledge of HTTP.
  • Why EventSource reconnects on its own, and why reconnection restores the transport but not the missed data.
  • Why proxies and compression can silently break SSE even when the Rust code is correct.

The Example

Everything lives in one file. A background task ticks once per second and publishes each tick into a broadcast channel; every open /events connection subscribes and streams the ticks out as SSE frames. / serves a tiny page that consumes the stream with EventSource. The payload is only a counter; everything else exists to make the concepts observable.

src/main.rs
use std::{convert::Infallible, time::Duration};

use axum::{
    Router,
    extract::State,
    response::{
        Html,
        sse::{Event, KeepAlive, Sse},
    },
    routing::get,
};
use futures_util::{Stream, StreamExt};
use tokio::sync::broadcast;
use tokio_stream::wrappers::BroadcastStream;

type Ticks = broadcast::Sender<u64>;

async fn events(State(tx): State<Ticks>) -> Sse<impl Stream<Item = Result<Event, Infallible>>> {
    let rx = tx.subscribe();

    let stream = BroadcastStream::new(rx).filter_map(|msg| async move {
        match msg {
            Ok(n) => Some(Ok(Event::default()
                .event("tick")
                .id(n.to_string())
                .data(format!("tick #{n}")))),
            Err(err) => {
                eprintln!("subscriber fell behind: {err}");
                None
            }
        }
    });

    Sse::new(stream).keep_alive(KeepAlive::new().interval(Duration::from_secs(10)))
}

async fn page() -> Html<&'static str> {
    Html(PAGE)
}

#[tokio::main]
async fn main() {
    let (tx, _) = broadcast::channel::<u64>(16);

    let producer = tx.clone();
    tokio::spawn(async move {
        let mut ticker = tokio::time::interval(Duration::from_secs(1));
        let mut n = 0u64;
        loop {
            ticker.tick().await;
            n += 1;
            let _ = producer.send(n); // Err means nobody is listening yet
        }
    });

    let app = Router::new()
        .route("/", get(page))
        .route("/events", get(events))
        .with_state(tx);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("open http://127.0.0.1:3000");
    axum::serve(listener, app).await.unwrap();
}

SSE in One Picture

An SSE endpoint is not a series of requests. It is one ordinary GET request whose response body stays open until it is closed or the connection drops.

  • The server answers 200 OK with Content-Type: text/event-stream and then keeps writing UTF-8 text frames.
  • Arrows only go server → browser inside that response. Anything the browser sends back uses separate normal requests.
  • It is plain HTTP: chunked transfer on HTTP/1.1, ordinary DATA frames on HTTP/2. Proxies see a normal response.
  • EventSource reconnects by itself when the connection drops, unlike a raw fetch stream.

The Wire Format

Before touching Rust, know what the browser actually parses. Each event is a few field: value lines followed by a blank line.

FieldMeaning
data:Payload. Multiple data: lines are joined with \n. axum splits embedded newlines for you.
event:Event type name. Omit it and the event is delivered as "message" (es.onmessage).
id:Last event id. On reconnect the browser sends it back as the Last-Event-ID header.
retry:Reconnect delay hint in milliseconds, for example retry: 3000.
: …Comment line. Ignored by the parser; used as heartbeats by KeepAlive.
blank lineDispatch boundary. Without it, the browser buffers the fields and delivers nothing.

Connection Lifecycle, in Plain English

The whole discussion reduces to four facts. Keep these straight and most SSE confusion disappears.

  1. One HTTP response. SSE is a single GET. The status and headers are sent once, then the server keeps appending bytes to the same response body. It is not a series of responses, and the client does not poll.
  2. The client reads incrementally. The browser's HTTP stack hands body bytes to EventSource as they arrive. EventSource buffers them and dispatches an event only when it sees the blank line. HTTP chunk boundaries and SSE event boundaries are unrelated.
  3. The server closes the stream. There is no SSE “end” event. When your stream returns None, hyper writes HTTP/1.1's terminating chunk (0\r\n\r\n) or sets HTTP/2's END_STREAM. The client can abort early with es.close() or by leaving the page, but the normal end-of-body signal is server-driven.
  4. The client reconnects. If the response ends or the connection fails, EventSource issues a new GET after the retry delay (about 3 seconds, or the last retry: hint), sending Last-Event-ID if it saw an id:. Reconnect restores the transport, not the data: the server must replay missed events. A valid SSE response that ends causes an endless close → reconnect loop; answer a reconnect with 204 to stop it. Silence on an open connection causes no reconnect — keep-alive comments just prevent idle timeouts.

Rule of thumb: keep the response open, send bytes when you have something (or a comment when you do not), and use 204 — not a clean close — to make clients stop.

Rust Streams, Briefly

axum's SSE body is a stream. If you know iterators, a stream is the async version: values are pulled one at a time, but the producer may need to wait between them.

  • Iterator::next returns Option<T> immediately. Stream::poll_next returns Poll::Pending and registers a waker when there is nothing yet.
  • StreamExt methods such as map, filter_map, and throttle are lazy adapters. Nothing runs until the response body is polled.
  • The stream must be Send + 'static: it is moved into the response and may be polled on another thread. Own your data; do not capture borrowed locals.
  • futures-util gives you the trait and combinators; tokio-stream adds adapters that turn Tokio channels into streams.

Fan-out with a broadcast Channel

Every browser needs its own response stream, yet all of them must see the same events. The problem is therefore one of fan-out: one source, many independent consumers. A Tokio broadcast channel is the seam that makes the source unaware of how many clients exist.

  • broadcast::channel(16) returns a Sender and one initial Receiver; tx.subscribe() creates a new receiver for each connection.
  • T must be Clone, because the same value is cloned into every receiver. Here u64 is Clone.
  • The capacity bounds how far behind any receiver may fall: the channel keeps at most 16 messages, so a receiver that falls further behind is told it lagged and loses the oldest events. Losing events is intentional; the alternative is unbounded memory growth.
  • Sender::send only fails when there are zero receivers. At startup, before any browser connects, that is normal — hence let _ =.

One Stream per Connection

The handler is where a connection becomes an independent consumer. It subscribes a fresh receiver, then maps channel items into SSE frames; everything downstream of that point is private to this one response.

src/main.rs:18-35
async fn events(State(tx): State<Ticks>) -> Sse<impl Stream<Item = Result<Event, Infallible>>> {
    let rx = tx.subscribe();

    let stream = BroadcastStream::new(rx).filter_map(|msg| async move {
        match msg {
            Ok(n) => Some(Ok(Event::default()
                .event("tick")
                .id(n.to_string())
                .data(format!("tick #{n}")))),
            Err(err) => {
                eprintln!("subscriber fell behind: {err}");
                None
            }
        }
    });

    Sse::new(stream).keep_alive(KeepAlive::new().interval(Duration::from_secs(10)))
}
  • State<Ticks> extracts a clone of the sender stored in the router. tx.subscribe() must happen inside the handler so each connection gets its own receiver.
  • BroadcastStream::new(rx) adapts the receiver into Stream<Item = Result<u64, BroadcastStreamRecvError>>. The error case is Lagged(n).
  • filter_map handles both variants: a good value becomes Some(Ok(event)); a lag error becomes None and is skipped. After that, the stream cannot fail, so the error type is Infallible.
  • The return type Sse<impl Stream<Item = Result<Event, Infallible>>> says “some unnamed concrete stream type” — the handler does not need to name FilterMap<BroadcastStream<…>, …>.
  • The receiver lives inside the returned stream. When the browser disconnects, hyper drops the body, the stream is dropped, and the receiver is cleaned up automatically.

Why log the lag error? It is the only signal that a client silently missed events. In production you might count it as a metric, or replay from a durable log using Last-Event-ID.

The Response Stays Open

An SSE response is ordinary HTTP that stays open rather than completing. The status and headers are sent once; the body stays open and is filled as the stream yields values. The client therefore learns about failure only when the connection breaks, and any intermediary may drop an idle connection unless something keeps it warm.

src/main.rs:23-26, 34
            Ok(n) => Some(Ok(Event::default()

                .id(n.to_string())
                .data(format!("tick #{n}")))),
            ...
    Sse::new(stream).keep_alive(KeepAlive::new().interval(Duration::from_secs(10)))
  • A frame is just text. Event is a formatter: .event("tick"), .id(...), and .data(...) choose which lines appear before the blank dispatch line. Add .retry(Duration) to send a reconnect-delay hint.
  • Sse is the adapter from stream items to an HTTP response. It sets Content-Type: text/event-stream and Cache-Control: no-cache; yielding an item is the only way bytes leave.
  • A quiet stream looks identical to a dead one to a proxy. KeepAlive emits a comment frame (:) so idle connections survive; the default interval is 15 seconds, here 10.
  • Subtle but important: keep-alives are only emitted while the stream is idle. Each real event resets the timer. With a tick every second you will never see one — that is correct, not a bug. Pause the producer for more than 10 seconds to observe it.

No flush calls needed. SSE is not “write and flush”: every event the stream yields is framed and sent. Backpressure comes from the socket, so a slow client stops polling rather than silently buffering forever in your task.

The Source Is Not HTTP

What happened and how it is delivered are separate concerns. The producer only puts values into the channel; it is blind to whether zero, one, or many clients are connected. That is why the same source could drive SSE, WebSockets, or a background job without changing.

            ticker.tick().await;
            n += 1;
            let _ = producer.send(n); // Err means nobody is listening yet
        }
    });

    let app = Router::new()
        .route("/", get(page))
        .route("/events", get(events))
        .with_state(tx);
}
  • tokio::spawn detaches the producer onto the runtime. Because it captures a cloned sender, it owns everything it needs and can outlive main's scope.
  • interval ticks forever and its first tick completes immediately, so the counter starts at 1 right away. The producer never waits for a client.
  • with_state(tx) stores the sender in the router; each request receives a clone through State<Ticks>. The state must be Clone because it is copied per request.
  • The initial receiver returned by broadcast::channel is dropped (_). Until the first browser subscribes, send returns Err — a normal zero-receiver state, not a failure.
  • The source could be a database change feed, a job progress reporter, or a webhook consumer; the SSE layer would stay identical.

The Browser Client

EventSource is the browser's built-in JavaScript API for consuming an SSE endpoint — it opens the request, parses incoming events, and reconnects automatically — so your code only handles events and connection state.

src/main.rs:75-86
    <script>
      const statusEl = document.getElementById("status");
      const logEl = document.getElementById("log");
      const es = new EventSource("/events");
      es.onopen = () => { statusEl.textContent = "connected"; };
      es.onerror = () => { statusEl.textContent = "reconnecting..."; };
      es.addEventListener("tick", (e) => {
        const li = document.createElement("li");
        li.textContent = `${e.data} (id=${e.lastEventId})`;
        logEl.prepend(li);
      });
    </script>
  • new EventSource("/events") issues one GET and starts parsing text/event-stream. You never read or parse the body yourself.
  • onopen fires when the response headers arrive and the connection is live; onerror fires when it drops. readyState tells you where you are: 0 CONNECTING, 1 OPEN, 2 CLOSED.
  • Because the server names events "tick", you must use addEventListener("tick", ...). onmessage only receives events without an event: field.
  • e.data is the payload string; e.lastEventId mirrors the id: field. On reconnect the browser sends Last-Event-ID, but your server must replay missed events — this example does not, so ticks during an outage are lost.
  • EventSource cannot set custom headers such as Authorization. For auth use same-site cookies or a token in the query string, and remember that the browser's per-host connection limit applies.

Common Pitfalls

1. “Keep-alive means the server keeps sending heartbeats.” It does not: KeepAlive is idle-triggered and resets whenever a real event is sent. To force a heartbeat on a busy stream, emit your own comment event on a timer. To verify the feature, stop sending events for longer than the keep-alive interval.

2. “If the Rust code is correct, events will arrive.” Compression middleware may hold back small chunks, and reverse proxies often buffer responses by default. Disable compression for text/event-stream, and configure nginx-style proxies with proxy_buffering off (plus X-Accel-Buffering: no if needed). axum sets Cache-Control: no-cache but cannot configure your proxy.

3. “Lagged is either fatal or safe to ignore.” Broadcast drops old messages for slow receivers and tells you only via Err(Lagged(n)). If you propagate that error, the SSE response ends. If you silently ignore it, clients miss data. Choose deliberately; size the channel and monitor lag.

4. “send returned Err, so the channel is broken.” At startup there are no receivers, so send returns Err even though everything is fine. Ignore it, or use tx.receiver_count() to check.

5. “An error in the stream can be recovered from.” The stream item is Result<Event, E>; an Err terminates the response. After mapping lag to None, Infallible documents that this stream cannot fail.

6. “The blank line is just formatting.” It is the dispatch boundary. If you implement the protocol manually (instead of using Event), a missing empty line means the browser buffers fields and shows nothing. Similarly, one data: line per newline is required. Event handles both.

7. “SSE can carry arbitrary bytes.” SSE is text-only. Encode bytes as base64 (and decode client-side), or use a WebSocket.

8. “Async makes locks harmless.” SSE handlers are async and long-lived. Holding a blocking std::sync mutex guard across an await point can deadlock or stall the runtime; drop the guard before awaiting, or use tokio::sync primitives.

9. “CORS only affects reading the response.” EventSource is subject to CORS. Cross-origin use needs Access-Control-Allow-Origin, and cookie auth needs withCredentials plus the right CORS credentials headers.

Key Takeaways

An SSE endpoint is one HTTP response whose body stays open rather than completing, so the server's job is to keep producing bytes rather than to answer repeatedly. Fan-out works because each connection gets its own stream fed from one shared source, and the channel's capacity makes event loss a deliberate policy. Keep-alives protect only idle connections, and proxies or compression can quietly buffer the stream even when the Rust code is correct.
