Authentication in Web Apps

Password login, server-side sessions, and protected routes — built with Axum, in the smallest example that is still honest about security.

How to Use

Create a project and add the exact dependency versions this tutorial was tested with (Rust 1.95, axum 0.8.9, argon2 0.6.0). Drop the @... parts to accept newer compatible releases. 

cargo new auth-demo
cd auth-demo
cargo add axum@0.8.9
cargo add tokio@1.54.1 --features full
cargo add serde@1.0.229 --features derive
cargo add serde_json@1.0.154
cargo add argon2@0.6.0
cargo add axum-extra@0.12.6 --features cookie
cargo add rand@0.10.3

Replace src/main.rs with the complete example further down, then start the server: 

cargo run

Leave that terminal running; the server listens on http://127.0.0.1:3000. It keeps users and sessions in memory, so restarting the process forgets everything. That is deliberate: it keeps the example runnable with no database.

What to observe

In a second terminal, run these in order. curl -c saves the cookie the server sends; -b sends it back. 

# 1. Register. The response is 201 Created.
curl -i -X POST http://127.0.0.1:3000/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"correct horse"}'

# 2. Log in. Saves the session cookie to jar.txt; response is 204.
curl -i -c jar.txt -X POST http://127.0.0.1:3000/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"correct horse"}'

# 3. Use the session. Response is 200 {"user":"alice"}.
curl -i -b jar.txt http://127.0.0.1:3000/me

# 4. Log out. Response is 200 and the cookie is expired.
curl -i -b jar.txt -c jar.txt -X POST http://127.0.0.1:3000/logout

# 5. The old cookie no longer works: 401 Unauthorized.
curl -i -b jar.txt http://127.0.0.1:3000/me

Expected highlights along the way:

HTTP/1.1 201 Created

HTTP/1.1 204 No Content
set-cookie: sid=d3dd3f3e...ee696; HttpOnly; SameSite=Strict; Path=/

{"user":"alice"}

set-cookie: sid=; Path=/; Max-Age=0; Expires=...

HTTP/1.1 401 Unauthorized

Also try /me with no cookie, a wrong password, and a duplicate username. They answer 401, 401, and 409 respectively.

The Example

A complete, runnable Axum service with four endpoints: POST /register, POST /login, GET /me, and POST /logout. It stores Argon2 hashes and session records in memory so there is nothing else to install. Read it once top to bottom; each section below quotes the part that matters. 

use std::collections::HashMap;
use std::sync::{Arc, Mutex};

use argon2::{
    password_hash::{phc::PasswordHash, PasswordHasher, PasswordVerifier},
    Argon2,
};
use axum::{
    extract::{Request, State},
    http::StatusCode,
    middleware::{self, Next},
    response::{IntoResponse, Response},
    routing::{get, post},
    Extension, Json, Router,
};
use axum_extra::extract::cookie::{Cookie, CookieJar, SameSite};
use rand::Rng;
use serde::Deserialize;
use serde_json::json;

const SESSION_COOKIE: &str = "sid";

// In-memory state: username -> PHC hash, and session token -> username.
#[derive(Clone)]
struct AppState {
    users: Arc<Mutex<HashMap<String, String>>>,
    sessions: Arc<Mutex<HashMap<String, String>>>,
}

#[derive(Deserialize)]
struct Credentials {
    username: String,
    password: String,
}

// One error type for every handler; it knows how to become an HTTP response.
enum AppError {
    Unauthorized(&'static str),
    Conflict(&'static str),
    Internal,
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, message) = match self {
            AppError::Unauthorized(m) => (StatusCode::UNAUTHORIZED, m),
            AppError::Conflict(m) => (StatusCode::CONFLICT, m),
            AppError::Internal => (StatusCode::INTERNAL_SERVER_ERROR, "internal error"),
        };
        (status, Json(json!({ "error": message }))).into_response()
    }
}

// A 256-bit random, hex-encoded opaque session identifier.
fn new_token() -> String {
    let mut bytes = [0u8; 32];
    rand::rng().fill_bytes(&mut bytes);
    bytes.iter().map(|b| format!("{b:02x}")).collect()
}

// POST /register: hash the password, never store the plaintext.
async fn register(
    State(state): State<AppState>,
    Json(creds): Json<Credentials>,
) -> Result<StatusCode, AppError> {
    let hash = Argon2::default()
        .hash_password(creds.password.as_bytes())
        .map_err(|_| AppError::Internal)?
        .to_string();

    let mut users = state.users.lock().unwrap();
    if users.contains_key(&creds.username) {
        return Err(AppError::Conflict("username already taken"));
    }
    users.insert(creds.username, hash);
    Ok(StatusCode::CREATED)
}

// POST /login: verify the password, mint a session, set an HttpOnly cookie.
async fn login(
    State(state): State<AppState>,
    jar: CookieJar,
    Json(creds): Json<Credentials>,
) -> Result<(CookieJar, StatusCode), AppError> {
    let stored = state.users.lock().unwrap().get(&creds.username).cloned();
    let valid = stored
        .and_then(|h| PasswordHash::new(&h).ok())
        .map(|parsed| {
            Argon2::default()
                .verify_password(creds.password.as_bytes(), &parsed)
                .is_ok()
        })
        .unwrap_or(false);

    if !valid {
        return Err(AppError::Unauthorized("invalid username or password"));
    }

    let token = new_token();
    state
        .sessions
        .lock()
        .unwrap()
        .insert(token.clone(), creds.username);

    let cookie = Cookie::build((SESSION_COOKIE, token))
        .path("/")
        .http_only(true)
        .same_site(SameSite::Strict)
        .build();

    Ok((jar.add(cookie), StatusCode::NO_CONTENT))
}

// Middleware: reject requests without a valid session before the handler runs.
async fn require_auth(
    State(state): State<AppState>,
    jar: CookieJar,
    mut request: Request,
    next: Next,
) -> Result<Response, StatusCode> {
    let user = jar
        .get(SESSION_COOKIE)
        .and_then(|c| state.sessions.lock().unwrap().get(c.value()).cloned());

    match user {
        Some(user) => {
            request.extensions_mut().insert(user);
            Ok(next.run(request).await)
        }
        None => Err(StatusCode::UNAUTHORIZED),
    }
}

// GET /me: only reachable through the auth middleware.
async fn me(Extension(user): Extension<String>) -> Json<serde_json::Value> {
    Json(json!({ "user": user }))
}

// POST /logout: delete the server-side session and clear the cookie.
async fn logout(State(state): State<AppState>, jar: CookieJar) -> CookieJar {
    if let Some(c) = jar.get(SESSION_COOKIE) {
        state.sessions.lock().unwrap().remove(c.value());
    }
    jar.remove(Cookie::build((SESSION_COOKIE, "")).path("/").build())
}

#[tokio::main]
async fn main() {
    let state = AppState {
        users: Arc::new(Mutex::new(HashMap::new())),
        sessions: Arc::new(Mutex::new(HashMap::new())),
    };

    let protected = Router::new()
        .route("/me", get(me))
        .route("/logout", post(logout))
        .route_layer(middleware::from_fn_with_state(state.clone(), require_auth));

    let app = Router::new()
        .route("/register", post(register))
        .route("/login", post(login))
        .merge(protected)
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on http://127.0.0.1:3000");
    axum::serve(listener, app).await.unwrap();
}

1. Authentication vs. authorization

Why it matters: "Who are you?" and "What may you do?" are different questions. Together they are the two halves of access control, and confusing them produces endpoints that check identity but never check permission.

Question Name Typical failure In this example
Who are you? Authentication 401 Unauthorized Login plus the session lookup
What may you do? Authorization 403 Forbidden Not implemented — every logged-in user can call /me

The example authenticates. It deliberately stops short of authorization: it proves the session belongs to Alice, but has no roles, ownership checks, or per-resource rules. Those would be additional checks after the identity is known. 

# src/main.rs:135-138
// GET /me: only reachable through the auth middleware.
async fn me(Extension(user): Extension<String>) -> Json<serde_json::Value> {
    Json(json!({ "user": user }))
}
  • The handler receives a String username from a request extension. It never parses a cookie itself, so it cannot accidentally trust client-supplied data.
  • Authentication happened earlier, in middleware. By the time me runs, the question "who?" already has an answer.

2. Passwords are hashed, never stored

Why it matters: a database leak must not hand the attacker working passwords. Hashing is one-way; encryption is reversible with a key. Store a password hash and verify by recomputing it. 

# src/main.rs:61-77
// POST /register: hash the password, never store the plaintext.
async fn register(
    State(state): State<AppState>,
    Json(creds): Json<Credentials>,
) -> Result<StatusCode, AppError> {

        .hash_password(creds.password.as_bytes())
        .map_err(|_| AppError::Internal)?
        .to_string();

    let mut users = state.users.lock().unwrap();
    if users.contains_key(&creds.username) {
        return Err(AppError::Conflict("username already taken"));
    }
    users.insert(creds.username, hash);
    Ok(StatusCode::CREATED)
}
# src/main.rs:85-93
    let stored = state.users.lock().unwrap().get(&creds.username).cloned();
    let valid = stored
        .and_then(|h| PasswordHash::new(&h).ok())
        .map(|parsed| {
            Argon2::default()
                .verify_password(creds.password.as_bytes(), &parsed)
                .is_ok()
        })
        .unwrap_or(false);
  • Argon2id is memory-hard and tunable. Being slow and memory-hungry is the point: it makes offline guessing expensive for an attacker who steals the hashes.
  • A salt is random data mixed into the hash. It is stored alongside the hash, so it is not secret; its job is to make precomputed tables useless and to stop two identical passwords from producing identical hashes.
  • hash_password generates the salt for you and returns a PHC string containing the algorithm, parameters, salt, and hash. Store that whole string.
  • Verification parses the PHC string and reuses its parameters and salt, then compares in constant time. There is no "decrypt" step — a hash cannot be reversed.

Version note. Older argon2 examples build a SaltString and call hash_password(password, &salt). That is the 0.5 API. In argon2 0.6 the salt is generated inside hash_password(password), and the parsed hash type moved to password_hash::phc::PasswordHash.

3. Sessions vs. tokens

Why it matters: HTTP is stateless. Every request must carry proof of identity again, and you must choose where that proof lives and how it can be revoked.

Server-side session (this example) Stateless token (e.g. JWT)
Browser holds A random, opaque session ID A signed token containing claims
Server stores A session record per login Nothing per session — just a signing key
Revocation Delete the record; effective immediately Hard; needs a denylist or short expiry
Scaling Needs a shared store (database, Redis) Any server with the key can verify
Size A tiny cookie A larger header or cookie

This example uses sessions because they make logout and revocation honest: the server can always answer "is this ID still valid?".

    users: Arc<Mutex<HashMap<String, String>>>,

}

    state
        .sessions
        .lock()
        .unwrap()

  • The map is the session store: sid → username. The client never learns anything except its own random ID.
  • A JWT would instead carry the username inside a signed token. The server could verify the signature without a lookup, but could not easily invalidate one token before it expires.
  • The Mutex is fine for a single-process demo. In production, sessions belong in a database or Redis so they survive restarts and work across instances.

4. Unguessable session IDs

Why it matters: the session ID is a bearer credential. Anyone who presents it is treated as that user, so it must be impossible to guess or enumerate. Treat it like a password that the server issued. 

# src/main.rs:54-59
// A 256-bit random, hex-encoded opaque session identifier.
fn new_token() -> String {
    let mut bytes = [0u8; 32];
    rand::rng().fill_bytes(&mut bytes);
    bytes.iter().map(|b| format!("{b:02x}")).collect()
}
  • 256 bits from the operating system's cryptographic RNG. Guessing one is not a realistic attack.
  • Never derive the ID from the username, a timestamp, or an incrementing counter. Those are predictable.
  • Rotate it on login (this code mints a fresh token every time) and invalidate the old one. A fresh ID after login also prevents session fixation.
  • Opaque means it encodes no data. All meaning lives in the server-side record, so a tampered value simply fails the lookup.

5. Session cookies

Why it matters: a cookie is how the browser automatically attaches the session ID to every request. Its attributes decide who can read it and when it is sent.

        .path("/")
        .http_only(true)
        .same_site(SameSite::Strict)
        .build();

    Ok((jar.add(cookie), StatusCode::NO_CONTENT))
set-cookie: sid=d3dd3f3e...ee696; HttpOnly; SameSite=Strict; Path=/
Attribute What it does Why you want it
HttpOnly Hides the cookie from document.cookie An XSS bug cannot read and exfiltrate the session ID
SameSite=Strict Does not send the cookie on cross-site requests Blocks classic CSRF; also affects external-link navigation
Secure Only sent over HTTPS Keeps the ID off plaintext connections; add it in production
Path=/ Scopes the cookie to the whole site Needed so logout can remove the same cookie
Max-Age Sets an explicit lifetime Limits how long a stolen ID stays useful

The example omits Secure so it works over http://localhost. On a real deployment, serve over HTTPS and set .secure(true). Never use SameSite=None without Secure; browsers reject that combination.

  • CookieJar is an extractor: it reads incoming Cookie headers and builds outgoing Set-Cookie headers.
  • You must return the updated jar from the handler (here in the tuple). If you drop it, the browser never receives the cookie.
  • The cookie carries only the random ID. Identity and expiry live on the server, out of the client's reach.

6. Guarding routes

Why it matters: checking authentication inside every handler is repetitive and easy to forget. One middleware in front of a route group makes the check impossible to skip. 

# src/main.rs:115-133
// Middleware: reject requests without a valid session before the handler runs.
async fn require_auth(
    State(state): State<AppState>,
    jar: CookieJar,
    mut request: Request,
    next: Next,
) -> Result<Response, StatusCode> {
    let user = jar
        .get(SESSION_COOKIE)
        .and_then(|c| state.sessions.lock().unwrap().get(c.value()).cloned());

    match user {
        Some(user) => {
            request.extensions_mut().insert(user);
            Ok(next.run(request).await)
        }
        None => Err(StatusCode::UNAUTHORIZED),
    }
}
# src/main.rs:155-164
    let protected = Router::new()
        .route("/me", get(me))
        .route("/logout", post(logout))
        .route_layer(middleware::from_fn_with_state(state.clone(), require_auth));

    let app = Router::new()
        .route("/register", post(register))
        .route("/login", post(login))
        .merge(protected)
        .with_state(state);
  • route_layer applies only to the routes already added to that router, so /me and /logout are protected while /register and /login stay public.
  • On success the middleware inserts the username into the request extensions. Handlers read it with Extension<String> instead of re-reading the cookie.
  • On failure it returns 401 and never calls next.run(...), so the handler cannot run.
  • This is also where authorization would go: after finding the user, check roles or ownership before letting the request through.

7. Logout and invalidation

Why it matters: deleting the browser cookie is not logout. If the server still has the session record, a copy of the ID — stolen earlier — keeps working. Logout must destroy the server-side state. 

# src/main.rs:140-146
// POST /logout: delete the server-side session and clear the cookie.
async fn logout(State(state): State<AppState>, jar: CookieJar) -> CookieJar {
    if let Some(c) = jar.get(SESSION_COOKIE) {
        state.sessions.lock().unwrap().remove(c.value());
    }
    jar.remove(Cookie::build((SESSION_COOKIE, "")).path("/").build())
}
Step Browser Server session store
Login Stores sid sid → alice
Protected request Sends sid Lookup succeeds
Logout Deletes sid Removes sid
Replay old sid Sends it anyway Lookup fails → 401
  • The removal cookie must use the same Path as the original, or the browser keeps the old one.
  • jar.remove(...) emits Max-Age=0 and a past expiry, telling the browser to delete it. That is a courtesy, not the security boundary.
  • Real sessions also need an expiry timestamp and periodic rotation. This demo has neither, so its sessions live until logout or restart.

8. CSRF

Why it matters: browsers attach cookies by destination domain, not by which page started the request. An attacker's page can therefore make the victim's browser send an authenticated request without the victim knowing. 

# src/main.rs:106-110
    let cookie = Cookie::build((SESSION_COOKIE, token))
        .path("/")
        .http_only(true)
        .same_site(SameSite::Strict)
        .build();
  • SameSite=Strict tells the browser not to send this cookie on cross-site requests. A forged form POST from evil.example arrives without the session cookie, so the server sees an anonymous request.
  • Defense in depth: for state-changing endpoints, also check a CSRF token (synchronizer token or double-submit cookie) and/or the Origin / Sec-Fetch-Site headers.
  • Never perform a state change on GET. A cross-site image or link can trigger a GET, and users expect GET to be safe.
  • Lax is the common compromise: it still blocks cross-site POSTs but lets the cookie be sent on top-level navigation from an external link, which Strict suppresses.

Common Pitfalls

Storing the password, or "encrypting" it. Reversible encryption means a stolen key reveals every password. Store an Argon2 hash and compare by recomputing.
Using the username as the session token. A cookie that says alice is trivially forged. The cookie must contain an unguessable value that the server maps to a user.
Trusting cookie contents. Cookies are client-controlled. This example treats the cookie as a lookup key only; the identity comes from the server-side record.
Forgetting to return the CookieJar. Adding a cookie to the jar does nothing unless the updated jar is part of the response. The handler must return it.
Clearing only the cookie on logout. The stolen session ID stays valid. Remove the server-side record first, then expire the cookie.
No expiry or rotation. Sessions should expire and should be reissued after login. This demo is intentionally minimal; production sessions need TTLs.
Hashing on the async runtime. Argon2 is deliberately expensive. Under load, run it inside tokio::task::spawn_blocking so it does not stall other requests on the executor.
User enumeration through timing or messages. Skipping the hash when the username is unknown makes "no such user" faster than "wrong password". Use one generic error and consider hashing a dummy password in the unknown-user branch.
No rate limiting. Even a slow hash is brute-forceable online without limits. Add per-account and per-IP throttling on /login.
Sending the session in a URL or localStorage. URLs leak through logs and Referer headers; localStorage is readable by XSS. Keep the session in an HttpOnly cookie.

Key Takeaways

Authentication is two pipelines: a slow, salted Argon2 hash when a password is created or checked, and a fast, opaque session lookup on every request. Keep the password out of storage and the session ID out of JavaScript's reach, and delete the server-side record on logout.

Sessions versus JWTs, SameSite versus CSRF tokens, expiries, rotation, and rate limits are trade-offs layered on those two ideas. Get the hashing and the server-side session lookup right first; everything else is a refinement.
