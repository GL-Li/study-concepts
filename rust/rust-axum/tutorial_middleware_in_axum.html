Middleware in Web Apps — with Axum

Wrap your handlers with reusable request/response logic using axum's tower-powered middleware.

How to Use

Create a new binary crate and add the crates the example needs. These are the current stable versions.

cargo new mw-demo --bin
cd mw-demo
cargo add axum@0.8
cargo add tokio@1 --features macros,rt-multi-thread,net
cargo add tower@0.5

Replace the contents of src/main.rs with the code in The Example, then start the server:

cargo run

Leave that terminal running. In a second terminal, send these requests:

curl -i http://127.0.0.1:3000/
curl -i http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/dashboard
curl -i -H "Authorization: Bearer secret" http://127.0.0.1:3000/dashboard
curl -i http://127.0.0.1:3000/missing

You should see one log line per request in the server terminal. In the responses, watch the x-request-number header on every request, the 401 when the token is missing, and the x-response-time header even on the 404.

The Example

One file, three small middleware functions, and two routes. It demonstrates logging, response headers, authentication that short-circuits, request extensions, shared state, ordering, and per-route middleware.

src/main.rs (complete, 124 lines)

use std::{
    net::SocketAddr,
    sync::{
        atomic::{AtomicU64, Ordering},
        Arc,
    },
    time::Instant,
};

use axum::{
    extract::{Extension, Request, State},
    http::{header, HeaderValue, StatusCode},
    middleware::{self, Next},
    response::Response,
    routing::get,
    Router,
};
use tower::ServiceBuilder;

#[derive(Clone)]
struct AppState {
    name: &'static str,
    hits: Arc<AtomicU64>,
}

#[derive(Clone)]
struct CurrentUser {
    name: String,
}

async fn log_and_time(req: Request, next: Next) -> Response {
    let method = req.method().clone();
    let uri = req.uri().clone();
    let start = Instant::now();

    let mut response = next.run(req).await;

    let ms = start.elapsed().as_secs_f64() * 1000.0;
    response
        .headers_mut()
        .insert("x-response-time", format!("{ms:.1}ms").parse::<HeaderValue>().unwrap());
    println!("{method} {uri} -> {} ({ms:.1} ms)", response.status());

    response
}

async fn require_token(mut req: Request, next: Next) -> Result<Response, StatusCode> {
    let token = req
        .headers()
        .get(header::AUTHORIZATION)
        .and_then(|value| value.to_str().ok());

    match token {
        Some("Bearer secret") => {
            req.extensions_mut().insert(CurrentUser {
                name: "Ada".to_string(),
            });
            Ok(next.run(req).await)
        }
        _ => Err(StatusCode::UNAUTHORIZED),
    }
}

async fn count_requests(State(state): State<AppState>, req: Request, next: Next) -> Response {
    let n = state.hits.fetch_add(1, Ordering::Relaxed) + 1;

    let mut response = next.run(req).await;
    response.headers_mut().insert(
        "x-request-number",
        n.to_string().parse::<HeaderValue>().unwrap(),
    );
    response
}

async fn home() -> &'static str {
    "public page: no token needed\n"
}

async fn health(State(state): State<AppState>) -> String {
    format!(
        "{} is ok ({} requests so far)\n",
        state.name,
        state.hits.load(Ordering::Relaxed)
    )
}

async fn dashboard(Extension(user): Extension<CurrentUser>) -> String {
    format!("private page: welcome, {}\n", user.name)
}

fn app(state: AppState) -> Router {
    let protected = Router::<AppState>::new()
        .route("/dashboard", get(dashboard))
        .route_layer(middleware::from_fn(require_token));

    Router::<AppState>::new()
        .route("/", get(home))
        .route("/health", get(health))
        .merge(protected)
        .layer(
            ServiceBuilder::new()
                .layer(middleware::from_fn_with_state(
                    state.clone(),
                    count_requests,
                ))
                .layer(middleware::from_fn(log_and_time)),
        )
        .with_state(state)
}

#[tokio::main]
async fn main() {
    let state = AppState {
        name: "middleware-demo",
        hits: Arc::new(AtomicU64::new(0)),
    };

    let app = app(state);
    let addr = SocketAddr::from(([127, 0, 0, 1], 3000));
    let listener = tokio::net::TcpListener::bind(addr).await.unwrap();

    println!("listening on http://{addr}");
    axum::serve(listener, app).await.unwrap();
}

1. What middleware is

Middleware is code that wraps request handling. It runs before the handler, can inspect or change the request, can call the handler, and can inspect or change the response on the way back out.

Why it matters: logging, authentication, CORS, compression, timeouts, and rate limiting are cross-cutting concerns. They do not belong to any single handler. Middleware lets you write them once and apply them to one route, a group of routes, or the whole application.

Why "handler" and not just "function"? "Function" names the language construct; "handler" names the role. A handler is the function that produces the response for a matched route, and axum requires the handler-compatible signature (extractors in, IntoResponse out). Middleware is also written as a function, but it receives Next and wraps the chain, so we call it middleware rather than a handler.

Other names for middleware. Frameworks use different words: filter (Java servlets, ASP.NET), interceptor (gRPC, Angular, NestJS), hook or plugin (broader extension points), aspect (AOP), and layer (tower, where it strictly means the wrapper factory). The contract differs, but the idea is the same: code that wraps or extends request handling.

The example composes three middleware functions. Two wrap the whole router, and one wraps only the protected route:

fn app(state: AppState) -> Router {
    let protected = Router::<AppState>::new()
        .route("/dashboard", get(dashboard))
        .route_layer(middleware::from_fn(require_token));

    Router::<AppState>::new()
        .route("/", get(home))
        .route("/health", get(health))
        .merge(protected)
        .layer(
            ServiceBuilder::new()
                .layer(middleware::from_fn_with_state(
                    state.clone(),
                    count_requests,
                ))
                .layer(middleware::from_fn(log_and_time)),
        )
        .with_state(state)
}
  • count_requests and log_and_time are applied with .layer(...), so they see every request, including unmatched paths.
  • require_token is applied with .route_layer(...) on the protected router, so it only runs for /dashboard.
  • A layer can call the handler (by calling next.run) or stop the request by returning a response itself. Both patterns are used here.

2. tower's Service and Layer

Axum does not define its own middleware trait. It reuses tower, the same abstraction used by hyper, tonic, and many other Rust networking libraries. Two traits explain almost everything:

  • A Service<Req> is something you can call with a request. It produces a response (asynchronously).
  • A Layer<Inner> is a factory that wraps an inner Service and returns a new Service.

Simplified mental model (not the real trait definitions)

// Simplified mental model, not the real trait definitions.
trait Service<Req> {
    type Response;
    async fn call(&mut self, req: Req) -> Self::Response;
}

trait Layer<Inner> {
    type Service;
    fn layer(&self, inner: Inner) -> Self::Service;
}

Axum's Router is itself a Service. Calling Router::layer(layer) is essentially layer.layer(router): the layer wraps the router and every route inside it.

middleware::from_fn is an adapter. It turns an ordinary async function into a Layer, so you get the ergonomics of a function without implementing Service and Layer by hand. The function receives the request and a Next value that represents the rest of the chain. When you need full control, such as capturing configuration or implementing poll_ready, implement tower::Layer and Service directly; the same composition rules apply.

3. from_fn and Next

middleware::from_fn turns an async function into middleware. The function's signature is strict, because axum must know which arguments are extractors and which one is the remainder of the chain.

src/main.rs:31–45

async fn log_and_time(req: Request, next: Next) -> Response {
    let method = req.method().clone();
    let uri = req.uri().clone();
    let start = Instant::now();

    let mut response = next.run(req).await;

    let ms = start.elapsed().as_secs_f64() * 1000.0;
    response
        .headers_mut()
        .insert("x-response-time", format!("{ms:.1}ms").parse::<HeaderValue>().unwrap());
    println!("{method} {uri} -> {} ({ms:.1} ms)", response.status());

    response
}
  • Zero or more FromRequestParts extractors come first (for example HeaderMap or State).
  • Exactly one FromRequest extractor comes second-to-last. This is usually the whole Request.
  • Next is always last.
  • The return type must implement IntoResponse, so Response, Result<Response, StatusCode>, and many other types work.

next.run(req).await is the only way to continue inward. If you never call it, the handler and any inner middleware never run. Next is not Clone, so call it once, and make sure every code path either returns early or calls it.

4. Reading and changing the request and response

Most observability and header-injection middleware has the same shape: capture some facts about the request, run the rest of the chain, then decorate the response.

src/main.rs:31–45

async fn log_and_time(req: Request, next: Next) -> Response {
    let method = req.method().clone();
    let uri = req.uri().clone();
    let start = Instant::now();

    let mut response = next.run(req).await;

    let ms = start.elapsed().as_secs_f64() * 1000.0;
    response
        .headers_mut()
        .insert("x-response-time", format!("{ms:.1}ms").parse::<HeaderValue>().unwrap());
    println!("{method} {uri} -> {} ({ms:.1} ms)", response.status());

    response
}
  • req.method(), req.uri(), and req.headers() give read-only access. Clone small values such as Method and Uri if you need them after the request moves on.
  • Take mut req only when you need to mutate it, for example to insert an extension.
  • Take mut response to change its status, headers, or body before returning it.
  • Header insertion is the most common response change. Use headers_mut().insert(...) with a parsed HeaderValue.

Body warning: a request body is a stream and can be consumed only once. If your middleware reads it to completion, the handler will see an empty body. Buffer it and rebuild the request, or avoid consuming it, unless replacing the body is the goal.

5. Short-circuiting a request

A middleware function does not have to call the handler. It can return a response immediately. That is how authentication, authorization, rate limiting, and validation reject requests before expensive work happens.

src/main.rs:47–62

async fn require_token(mut req: Request, next: Next) -> Result<Response, StatusCode> {
    let token = req
        .headers()
        .get(header::AUTHORIZATION)
        .and_then(|value| value.to_str().ok());

    match token {
        Some("Bearer secret") => {
            req.extensions_mut().insert(CurrentUser {
                name: "Ada".to_string(),
            });
            Ok(next.run(req).await)
        }
        _ => Err(StatusCode::UNAUTHORIZED),
    }
}
  • The success path inserts the user and calls next.run(req).await.
  • The failure path returns Err(StatusCode::UNAUTHORIZED) without calling next. The handler is skipped entirely.
  • Returning Result<Response, StatusCode> works because both variants implement IntoResponse. Returning a plain Response is equally valid.
  • Outer middleware still sees the rejection response. That is why the 401 in the example still carries x-response-time and x-request-number: it bubbles back out through the outer layers.

Prefer returning a status code or an error response over panicking. A panic in middleware can abort the connection instead of producing a clean HTTP response.

The hardcoded Bearer secret is for demonstration only. Real authentication should verify signed tokens, expiry, and scopes instead of comparing a literal string.

6. Passing data with request extensions

Extensions are a typed, per-request map stored on the request. A middleware inserts a value; a handler extracts it by type. This is how the auth middleware tells the dashboard handler who the user is without putting user data in a global.

src/main.rs:87–89 (extract)

async fn dashboard(Extension(user): Extension<CurrentUser>) -> String {
    format!("private page: welcome, {}\n", user.name)
}
  • Insert before calling next.run; the handler can only extract what is already there.
  • The type is the key. Extension<CurrentUser> retrieves exactly the value inserted as CurrentUser.
  • The value must be Clone + Send + Sync + 'static, because extensions may be cloned across the async machinery.
  • Extensions live for one request only. For data shared across requests, use router state (next section).

Missing extension: Extension<T> rejects with a 500 Internal Server Error if nothing was inserted, which usually means the middleware did not run. If the value is optional, extract Option<Extension<T>> instead.

7. Shared state in middleware

middleware::from_fn cannot extract State. When a middleware needs the application state, build it with middleware::from_fn_with_state. It captures a clone of the state when the layer is constructed, then provides it to the State extractor on every request.

  • Use from_fn_with_state rather than reaching for a global. It keeps dependencies explicit and testable.

8. Layer ordering

Layers wrap each other like an onion. The outermost layer runs first on the request and last on the response. The only question is which layer ends up outermost.

How you write it Outermost layer Request path
ServiceBuilder::new()
.layer(count_requests)
.layer(log_and_time)		 count_requests count_requests → log_and_time → handler
Router::new()
.layer(count_requests)
.layer(log_and_time)		 log_and_time log_and_time → count_requests → handler

The response always takes the reverse path, so the outermost layer is also the last one to touch the response. In the first row the response is handler → log_and_time → count_requests; in the second row it is handler → count_requests → log_and_time.

Why the difference? ServiceBuilder treats its layers as one ordered list: first added means outermost. A separate .layer(...) call wraps the router that already includes the earlier layers, so the last call becomes the new outermost wrapper.

The comparison is not Router::new() versus ServiceBuilder::new(); the two are normally used together, as in the example. The difference is whether the layers are combined into one composed layer by ServiceBuilder or applied one at a time by repeated Router::layer calls.

Rule of thumb: read ServiceBuilder top-to-bottom; read repeated .layer(...) calls bottom-to-top. That is the order the request follows.

src/main.rs:100–107

        .layer(
            ServiceBuilder::new()
                .layer(middleware::from_fn_with_state(
                    state.clone(),
                    count_requests,
                ))
                .layer(middleware::from_fn(log_and_time)),
        )

The example uses ServiceBuilder, so count_requests is outermost: request → count_requests → log_and_time → require_token (only on /dashboard) → handler. The response travels back in reverse.

9. layer versus route_layer

Authentication usually belongs on some routes, not all of them. route_layer applies middleware only when a route in that router matches. layer applies to everything the router serves, including the fallback that produces 404 responses.

src/main.rs:91–109

fn app(state: AppState) -> Router {
    let protected = Router::<AppState>::new()
        .route("/dashboard", get(dashboard))
        .route_layer(middleware::from_fn(require_token));

    Router::<AppState>::new()
        .route("/", get(home))
        .route("/health", get(health))
        .merge(protected)
        .layer(
            ServiceBuilder::new()
                .layer(middleware::from_fn_with_state(
                    state.clone(),
                    count_requests,
                ))
                .layer(middleware::from_fn(log_and_time)),
        )
        .with_state(state)
}
MethodApplies toRuns on a 404?
.layer(...)All routes and the fallbackYes
.route_layer(...)Only routes registered in that routerNo
  • The protected router is built separately and merged, so require_token guards only /dashboard. The Router::<AppState>::new() annotation keeps both routers on the same state type so they can be merged.
  • The outer .layer(...) call wraps the merged router, so logging and counting cover public routes, protected routes, and unmatched paths.
  • This is why /missing in the example still receives x-request-number and x-response-time headers.
  • route_layer is not a way to add middleware for the fallback. If you need fallback-only behavior, configure the fallback explicitly or use layer.

10. Built-in middleware: tower-http

You rarely need to write logging, timeouts, CORS, compression, or request IDs from scratch. tower-http provides production-ready layers that plug into the same ServiceBuilder.

Optional add-on to src/main.rs (not part of the runnable example)

use std::time::Duration;
use tower_http::{timeout::TimeoutLayer, trace::TraceLayer};

// Add these layers to the router from the main example.
let app = Router::new()
    .route("/", get(home))
    .layer(
        ServiceBuilder::new()
            // Outermost: one span / log line per request.
            .layer(TraceLayer::new_for_http())
            // Inner: abort slow handlers with 408 Request Timeout.
            .layer(TimeoutLayer::with_status_code(
                StatusCode::REQUEST_TIMEOUT,
                Duration::from_secs(5),
            )),
    );

Add the crate and enable only the features you use:

Add the dependency

cargo add tower-http@0.7 --features trace,timeout,cors
  • TraceLayer emits a tracing span per request. Install a tracing-subscriber to see the output.
  • TimeoutLayer aborts requests that exceed a duration. The example uses with_status_code to return 408 Request Timeout explicitly.
  • CorsLayer, CompressionLayer, RequestIdLayer, SetRequestIdLayer, and others cover common HTTP concerns.
  • Order matters here too: tracing is usually outermost, timeouts apply to the work inside, and CORS is often placed so that error responses still carry the CORS headers.

Common Pitfalls

Forgetting to call next.run. If you neither return early on purpose nor call next, the handler silently never runs. Every path should be deliberate.
Using from_fn with State. from_fn does not extract router state. Use from_fn_with_state, or extract the state from request extensions instead.
Putting extractors in the wrong order. The whole Request must be second-to-last and Next must be last. Anything before the request must be a FromRequestParts extractor.
Assuming Router::layer runs top to bottom. With repeated .layer(a).layer(b) calls, b wraps a. Use ServiceBuilder when you want the source order to match the request order.
Using layer for auth and wondering why public routes are protected. Use route_layer on a router that contains only the protected routes.
Expecting route_layer to run for 404s. It only runs when a route matches. Use layer, or an explicit fallback, if you need unmatched requests covered.
Forgetting the extension value. A missing Extension<T> produces a 500, not a 404. Make sure the middleware that inserts the value actually ran, or use Option<Extension<T>>.
Consuming the request body. Reading the body in middleware leaves nothing for the handler. Buffer and rebuild the request if you must inspect it.
Blocking inside an async middleware. Filesystem, CPU-heavy, or synchronous network work blocks the Tokio worker. Use spawn_blocking or an async client.

Key Takeaways

Axum middleware is ordinary async Rust wrapped in tower's Service and Layer abstractions: work before next.run, work after it, or stop the request by returning a response yourself. Choose the composition order deliberately, use route_layer for per-route concerns such as authentication, and use from_fn_with_state plus request extensions to pass context inward. Reach for tower-http before hand-writing the common HTTP concerns.
