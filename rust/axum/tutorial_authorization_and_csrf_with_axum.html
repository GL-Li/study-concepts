Authorization + CSRF with Axum

Authentication tells you who is calling. Authorization decides what they may do. CSRF protection proves that a state-changing request came from your page, not from an attacker's form riding the victim's cookies.

How to Use

This example is API-only, so curl is the whole interface. That is deliberate: the browser behaviour that makes CSRF possible (cookies attached automatically to requests for a site) is exactly what these commands reproduce.

Create the project and add the exact dependency versions the example uses:

bash
cargo new authz_csrf --bin
cd authz_csrf
cargo add axum@0.8.9
cargo add axum-extra@0.12.6 --features cookie
cargo add serde@1.0.229 --features derive
cargo add tokio@1.54.1 --features full
cargo add uuid@1.29.3 --features v4

Replace src/main.rs with the full program from The Example, then run it:

bash
cargo run

You should see:

text
listening on http://127.0.0.1:3000

Observe the concepts

Run these requests in order. Each one isolates a different failure or success:

bash
BASE=http://127.0.0.1:3000

# 1. Authentication: no session cookie -> 401.
curl -s -o /dev/null -w 'no session: %{http_code}\n' "$BASE/notes"

# 2. Log in as alice. Cookies are saved; the CSRF token is readable.
curl -s -c alice.jar -d 'username=alice' "$BASE/login"
ALICE_CSRF=$(awk '$6=="csrf"{print $7}' alice.jar)

# 3. Ownership on reads: alice sees only her own note.
curl -s -b alice.jar "$BASE/notes"

# 4. Ownership on writes: a valid token does not let alice delete bob's note.
curl -s -b alice.jar -o /dev/null -w 'not my note: %{http_code}\n' \
  -d "csrf=$ALICE_CSRF" "$BASE/notes/2/delete"

# 5. CSRF: alice deleting her OWN note without the token -> 403.
curl -s -b alice.jar -o /dev/null -w 'no token: %{http_code}\n' \
  -d '' "$BASE/notes/1/delete"

# 6. RBAC: alice cannot reach the admin page.
curl -s -b alice.jar -o /dev/null -w 'admin as alice: %{http_code}\n' "$BASE/admin"

# 7. Log in as admin; admins see every note, including bob's script payload.
curl -s -c admin.jar -d 'username=admin' "$BASE/login" >/dev/null
ADMIN_CSRF=$(awk '$6=="csrf"{print $7}' admin.jar)
curl -s -b admin.jar "$BASE/notes"

# 8. RBAC: the admin page now succeeds.
curl -s -b admin.jar -o /dev/null -w 'admin as admin: %{http_code}\n' "$BASE/admin"

# 9. Admin override: an admin may delete another user's note.
curl -s -b admin.jar -o /dev/null -w 'admin delete: %{http_code}\n' \
  -d "csrf=$ADMIN_CSRF" "$BASE/notes/2/delete"

Expected output:

text
no session: 401
logged in as alice
<h1>Notes</h1><ul><li>#1 alice: alice's note</li></ul>
not my note: 403
no token: 403
admin as alice: 403
<h1>Notes</h1><ul><li>#1 alice: alice's note</li><li>#2 bob: &lt;script&gt;alert('xss')&lt;/script&gt;</li><li>#3 bob: bob's second note</li></ul>
admin as admin: 200
admin delete: 200
What to observe: 401 means the caller is unknown; 403 means the caller is known but the action is forbidden. Step 4 shows that a valid CSRF token proves intent, not permission: alice is allowed to submit the form, but she does not own bob's note. Step 5 shows the reverse: alice owns the note, but without the token the request is rejected. Step 7 shows the XSS defense: the seeded <script> payload is rendered as text, not executed.

What You'll Learn

  • Why authentication ("who") and authorization ("what, on which object") are separate decisions, and why 401 and 403 signal different failures.
  • Why a session cookie should be an opaque key to server-side state, not a statement of identity the client can edit.
  • How RBAC replaces per-user permission lists with roles, and why that scales.
  • Why ownership is a per-object check, and how skipping it creates IDOR (insecure direct object references).
  • Why CSRF works: browsers attach cookies automatically, so a cross-site request can be authenticated without the user's intent.
  • Why a synchronizer token proves intent: the attacker cannot read a per-session secret.
  • When double-submit cookies work without server storage, and what they trust instead.
  • Why SameSite, HttpOnly, and Secure are layers, not substitutes for a CSRF token.
  • Why XSS is a different trust failure that can read the CSRF token and defeat it.
  • Why safe methods and correct status codes are part of the security model.

Key terms

Four acronyms carry the whole tutorial. Here is the short version before the requests make them concrete.

CSRF — Cross-Site Request Forgery
An attack that makes a logged-in user's browser send a state-changing request to a site the user trusts, without the user's intent. The browser attaches the user's cookies automatically, so the request looks authenticated; the attacker never needs to read the response.
RBAC — Role-Based Access Control
An authorization model where permissions are grouped into roles (for example user and admin) and each user is assigned one or more roles. A request is allowed only if the user's role grants it.
XSS — Cross-Site Scripting
An injection attack where attacker-controlled text is rendered as executable code (usually JavaScript) in another user's browser, under your site's origin. XSS can read tokens, call authenticated endpoints, and exfiltrate data.
IDOR — Insecure Direct Object Reference
An authorization bug where changing an identifier in a request (for example /notes/1 to /notes/2) gives access to an object the user does not own. Per-object ownership checks prevent it.

// ---------- authentication: who is calling? ----------

struct CurrentUser {
    username: String,
    role: Role,
    csrf: String,
}

impl FromRequestParts<AppState> for CurrentUser {
    type Rejection = Response;

    async fn from_request_parts(
        parts: &mut Parts,
        state: &AppState,
    ) -> Result<Self, Self::Rejection> {
        let jar = CookieJar::from_request_parts(parts, state).await.unwrap();
        let sid = jar
            .get("sid")
            .map(|c| c.value().to_owned())
            .ok_or_else(|| (StatusCode::UNAUTHORIZED, "login required").into_response())?;

        // The server looks up the session; the cookie is only an opaque key.
        let sessions = state.sessions.read().await;
        let session = sessions
            .get(&sid)
            .ok_or_else(|| (StatusCode::UNAUTHORIZED, "login required").into_response())?;

        Ok(CurrentUser {
            username: session.username.clone(),
            role: session.role,
            csrf: session.csrf.clone(),
        })
    }
}

// ---------- authorization #1: roles ----------

struct AdminUser(CurrentUser);

impl FromRequestParts<AppState> for AdminUser {
    type Rejection = Response;

    async fn from_request_parts(
        parts: &mut Parts,
        state: &AppState,
    ) -> Result<Self, Self::Rejection> {
        let user = CurrentUser::from_request_parts(parts, state).await?;
        if user.role == Role::Admin {
            Ok(AdminUser(user))
        } else {
            Err((StatusCode::FORBIDDEN, "admin only").into_response())
        }
    }
}

// ---------- CSRF: a per-session secret ----------

fn token_ok(expected: &str, submitted: &str) -> bool {
    let (expected, submitted) = (expected.as_bytes(), submitted.as_bytes());
    if expected.len() != submitted.len() {
        return false;
    }
    let mut diff = 0u8;
    for (a, b) in expected.iter().zip(submitted) {
        diff |= a ^ b;
    }
    diff == 0
}

fn csrf_ok(user: &CurrentUser, submitted: &str) -> Result<(), Response> {
    // The submitted form field must match the server's copy of the token.
    if token_ok(&user.csrf, submitted) {
        Ok(())
    } else {
        Err((StatusCode::FORBIDDEN, "invalid or missing CSRF token").into_response())
    }
}

#[derive(Deserialize)]
struct LoginForm {
    username: String,
}

#[derive(Deserialize)]
struct DeleteForm {
    #[serde(default)]
    csrf: String,
}

// ---------- handlers ----------

async fn login(
    State(state): State<AppState>,
    jar: CookieJar,
    Form(form): Form<LoginForm>,
) -> Result<(CookieJar, String), Response> {
    let role = match form.username.as_str() {
        "admin" => Role::Admin,
        "alice" | "bob" => Role::User,
        _ => return Err((StatusCode::UNAUTHORIZED, "unknown user").into_response()),
    };

    let sid = uuid::Uuid::new_v4().simple().to_string();
    let csrf = uuid::Uuid::new_v4().simple().to_string();
    state.sessions.write().await.insert(
        sid.clone(),
        Session {
            username: form.username.clone(),
            role,
            csrf: csrf.clone(),
        },
    );

    // The session cookie is hidden from JavaScript; the CSRF token is readable.
    let sid_cookie = Cookie::build(("sid", sid))
        .http_only(true)
        .same_site(SameSite::Strict)
        .path("/")
        .build();
    let csrf_cookie = Cookie::build(("csrf", csrf))
        .same_site(SameSite::Strict)
        .path("/")
        .build();

    Ok((
        jar.add(sid_cookie).add(csrf_cookie),
        format!("logged in as {}\n", form.username),
    ))
}

async fn notes(user: CurrentUser, State(state): State<AppState>) -> Html<String> {
    let notes = state.notes.read().await;
    let mut visible: Vec<(&u64, &Note)> = notes
        .iter()
        .filter(|(_, note)| user.role == Role::Admin || note.owner == user.username)
        .collect();
    visible.sort_by_key(|(id, _)| **id);

    let mut out = String::from("<h1>Notes</h1><ul>");
    for (id, note) in visible {
        out.push_str(&format!(
            "<li>#{} {}: {}</li>",
            id,
            escape(&note.owner),
            escape(&note.body)
        ));
    }
    out.push_str("</ul>\n");
    Html(out)
}

async fn delete_note(
    user: CurrentUser,
    State(state): State<AppState>,
    Path(id): Path<u64>,
    Form(form): Form<DeleteForm>,
) -> Result<&'static str, Response> {
    // CSRF proves the request came from the user's page; it does not grant permission.
    csrf_ok(&user, &form.csrf)?;

    let mut notes = state.notes.write().await;
    let owner = notes
        .get(&id)
        .map(|note| note.owner.clone())
        .ok_or_else(|| (StatusCode::NOT_FOUND, "no such note").into_response())?;

    // Authorization #2: being logged in is not the same as owning this note.
    if owner != user.username && user.role != Role::Admin {
        return Err((StatusCode::FORBIDDEN, "not your note").into_response());
    }

    notes.remove(&id);
    Ok("deleted\n")
}

async fn admin(AdminUser(user): AdminUser) -> String {
    format!("admin panel for {}\n", user.username)
}

// XSS: user text must be escaped before it becomes HTML.
fn escape(s: &str) -> String {
    s.replace('&', "&amp;")
        .replace('<', "&lt;")
        .replace('>', "&gt;")
        .replace('"', "&quot;")
}

#[tokio::main]
async fn main() {
    let state = AppState::new();
    let app = Router::new()
        .route("/login", post(login))
        .route("/notes", get(notes))
        .route("/notes/{id}/delete", post(delete_note))
        .route("/admin", get(admin))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on http://127.0.0.1:3000");
    axum::serve(listener, app).await.unwrap();
}
Why no HTML pages? A browser form would submit the same fields and the browser would attach the same cookies. Removing the page code keeps the example small while leaving the security mechanics unchanged. A real page would put the token in a hidden <input>; here curl reads it from the readable csrf cookie and sends it in the form body.
Why note #2 contains a script tag? It is a deliberately unsafe note body. Listing notes as an admin shows it escaped, which makes the XSS defense observable without adding a "create note" endpoint.

Authentication vs authorization

Why it matters: They answer different questions, and mixing them up creates both security holes and misleading status codes.

Authentication answers "who is calling?". Authorization answers "may this caller do this, to this object?". A request can pass the first and still fail the second.

Is the request well formed?Missing field or bad payload422 Unprocessable EntityMalformed form body
Did the request succeed?No failure200 OKDeleting a note you own

  • 401 is not 403. 401 means "I do not know who you are"; 403 means "I know exactly who you are, and this is forbidden".
  • Authentication is a prerequisite, not a permission. Proving a request comes from alice says nothing about whether alice may touch a particular note.
  • Status codes are part of the API. Clients and proxies act on them, so they should reflect the real reason a request failed.

Session identity: a cookie is a key

Why it matters: If the client can promote itself by editing a cookie, every later authorization check is built on sand.

The session cookie should carry an opaque random id. The server maps that id to a session record containing the username, role, and CSRF token. The client's only power is to present the key.

  • Server-side truth: identity and role come from the session store, never from a username or role in the request body.
  • Opaque key: the cookie contains no username, role, or signature the client can reason about or forge.
  • Typed gate: a handler that takes a CurrentUser cannot accidentally run unauthenticated; the type makes the check hard to forget.
  • New session per login: logging in issues a fresh id and token, so an old session cannot be reused or fixed.

RBAC: Role-Based Access Control

Why it matters: Roles let you describe who may do a kind of action once, instead of repeating permission lists for every user and route.

RBAC (Role-Based Access Control) groups permissions into roles such as user and admin, then assigns roles to users. The code asks "does this user's role grant this action?" rather than "is this user alice?".

rustsrc/main.rs:107–123

        parts: &mut Parts,
        state: &AppState,

        let user = CurrentUser::from_request_parts(parts, state).await?;
        if user.role == Role::Admin {
            Ok(AdminUser(user))
        } else {
            Err((StatusCode::FORBIDDEN, "admin only").into_response())
        }
    }
}
  • Coarse-grained: roles answer "may you use the admin panel?"; they do not answer "may you delete note #2?". Ownership handles that.
  • 403, not 401: the caller is authenticated; they simply lack the role.
  • Hard to bypass accidentally: the admin handler takes an AdminUser, so a plain authenticated user cannot satisfy its signature.
  • Keep roles few: a small set of roles is easier to reason about than a per-user permission matrix.

Ownership: authorize the object

Why it matters: Authentication and roles are about the caller; ownership is about the specific object being touched.

This is where IDOR (insecure direct object reference) lives. An authenticated user changes /notes/1/delete to /notes/2/delete and, if the server only checked "are you logged in?", deletes someone else's note. The check must load the note and compare its stored owner.

  • Load, check, then mutate: fetch the object, compare its owner (or an explicit admin override), and only then change it.
  • Never trust an owner from the request: the owner must come from the stored object or the session, never from a client-supplied field.
  • Filter reads too: alice's list must not contain bob's notes; hiding data and denying access are separate checks.
  • 403 vs 404: 403 confirms the object exists; 404 hides that fact. Choose deliberately and stay consistent.

CSRF: Cross-Site Request Forgery

Why it matters: A request can be fully authenticated and still not be something the user intended; CSRF is the gap between those two facts.

CSRF (Cross-Site Request Forgery) makes a logged-in user's browser send a state-changing request to a site the user trusts, without the user's intent. The browser attaches the user's cookies automatically, so the request is genuinely authenticated. The attacker does not need to read the response, only to cause the side effect.

The browser chooses cookies by destination, not by who started the request. If the victim is logged in and an attacker's page auto-submits a form to /notes/2/delete, the browser sends the victim's sid cookie with it.

        .same_site(SameSite::Strict)

  • A valid session is not user intent: the cookie proves the browser has a session, not that the user chose this action.
  • Cross-site forms are "simple requests": a form POST with application/x-www-form-urlencoded does not trigger a CORS preflight. The attacker cannot read the response, but the request is still sent.
  • Only state-changing requests need the check: GET must stay safe and idempotent. If GET /notes/2/delete deleted a note, an <img> tag would be enough to trigger it.
  • The cookie is the delivery vehicle: sid is what gets attached automatically; the readable csrf cookie is only a way to hand the token to the page or client.

Synchronizer token: proof of intent

Why it matters: If the page and the server share a per-session secret that the attacker cannot read, echoing that secret becomes evidence that the user's page sent the request.

A synchronizer token is generated at login, stored in the session, and echoed by every state-changing request. The attacker can send any field they like, but they cannot guess or read the secret. The server compares the submitted value with its own copy.

fn token_ok(expected: &str, submitted: &str) -> bool {
    let (expected, submitted) = (expected.as_bytes(), submitted.as_bytes());
    if expected.len() != submitted.len() {
        return false;
    }
    let mut diff = 0u8;
    for (a, b) in expected.iter().zip(submitted) {
        diff |= a ^ b;
    }
    diff == 0
}
  • Per-session and random: each login gets a fresh token. A global token shared by all users is effectively public.
  • Compared to the server's copy: the submitted field is checked against Session.csrf, not against the csrf cookie. That is what makes this a synchronizer token rather than double-submit.
  • Proof of intent, not permission: a correct token says the page sent the request; it does not say the user may delete this particular note. Both checks are required.
  • Constant-time comparison: avoids leaking how many leading bytes matched. The fix is cheap, so use it.
A missing token should be a deliberate rejection. If the body schema treats the token as required, a request with no token can fail as malformed (422) before your authorization logic runs. Parse it leniently, then reject it explicitly in the check (403), so the status code reflects the security decision.

Double-submit cookie: stateless defense

Why it matters: If you cannot store a token per session, you can still compare something the browser has with something the page sends.

The double-submit pattern puts a random value in a readable cookie and requires the page to echo it in a form field or header. The server compares the two and needs no session store. The example above does not use this pattern; it compares against the session instead.

SameSite, HttpOnly, Secure

Why it matters: Cookie attributes reduce how a cookie can leak or travel, but none of them proves who initiated a request.

  • Same-site is not same-origin: "site" is usually the registrable domain, while "origin" is scheme + host + port. Two subdomains are same-site but different origins.
  • Defense in depth: use SameSite, a CSRF token, CORS rules, and output encoding together. Each covers a gap the others miss.

XSS: Cross-Site Scripting

Why it matters: CSRF assumes the attacker cannot read your page; XSS breaks that assumption by letting the attacker run code on your origin.

XSS (Cross-Site Scripting) is an injection attack where untrusted text becomes executable code (usually JavaScript) in another user's browser, under your site's origin. It comes in reflected, stored, and DOM-based forms. XSS can read the CSRF token from the DOM or the readable cookie, call authenticated endpoints directly, and exfiltrate data.

CSRF and XSS are complementary threats: CSRF abuses the browser's automatic attachment of credentials, while XSS abuses the browser's execution of code your site served. A CSRF token is not an XSS defense.

// XSS: user text must be escaped before it becomes HTML.
fn escape(s: &str) -> String {
    s.replace('&', "&amp;")
        .replace('<', "&lt;")
        .replace('>', "&gt;")
        .replace('"', "&quot;")
}

APIs and header tokens

Why it matters: The defense is the same; only the delivery changes when the client is a script instead of a form.

SPAs and mobile clients often send JSON rather than forms. They can send the same token in an X-CSRF-Token header. A custom header cannot be set by a cross-site HTML form and it triggers a CORS preflight, so the attacker's origin must be explicitly allowed.

rustvariant (not in the example)
use axum::http::HeaderMap;

fn token_from_header(headers: &HeaderMap, expected: &str) -> bool {
    headers
        .get("x-csrf-token")
        .and_then(|value| value.to_str().ok())
        .map(|value| token_ok(expected, value))
        .unwrap_or(false)
}
  • Bearer tokens are different: an Authorization header is not attached automatically, so bearer-token APIs are not CSRF-prone in the same way. Token theft via XSS is the bigger risk.
  • CORS is not CSRF protection: an overly permissive Access-Control-Allow-Origin with credentials can undo the benefit. Allowlist origins; never combine * with credentials.
  • Keep tokens out of URLs: query strings leak into logs, browser history, and Referer headers.

Common pitfalls

  • "A logged-in request is a user-intended request." CSRF exists precisely because the first does not imply the second.
  • "Authentication implies authorization." Knowing the caller says nothing about what they may do or which objects they may touch.
  • "If the UI hides it, the server is protected." Hiding a button is not a security control; the endpoint must enforce the rule.
  • "A valid CSRF token grants permission." The token proves intent only. Alice can submit a valid token and still be forbidden from deleting bob's note.
  • "A CSRF token protects against XSS." If the attacker can run code on your origin, they can read the token. XSS defeats CSRF.
  • "SameSite solves CSRF completely." It helps a lot, but same-site subdomains, older clients, and non-browser clients remain gaps.
  • "HttpOnly prevents CSRF." It stops JavaScript from reading the cookie; the browser still sends it cross-site.
  • "CORS prevents CSRF." CORS stops the attacker from reading the response, not from causing a simple request to be sent.
  • "GET is fine for deletes." Then an image tag or a link preview can trigger the delete; keep state changes on unsafe methods.
  • "403 and 404 are interchangeable." One reveals that the object exists; the other hides it. Choose deliberately.
  • "Roles are enough." Role checks are coarse; without per-object ownership checks you still have IDOR.
  • "One global CSRF token is fine." A token shared by all users is effectively public. Use one per session.
  • "Login is not state-changing, so it needs no protection." Login CSRF can log a victim into the attacker's account.

Key Takeaways

Authentication, roles, and ownership answer three different questions, and a request can pass the first and still fail the others. CSRF is not an authentication failure: it is the browser attaching a valid credential to a request the user did not intend, so a per-session token the attacker cannot read is what proves intent. XSS is the exception that breaks that proof, which is why output encoding and CSRF defense must be deployed together.
